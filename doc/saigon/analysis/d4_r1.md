## 0. Executive summary (what Part B must know)

1. **Depend on `dda` and override it. Do not replace core.** C++ holds at least **2,426 unique hardcoded
   `(type,id)` string_id constants** (4,724 declarations) across ~30 id types (§3). A standalone `"core": true` TC
   would have to re-supply all of them, and only one core mod can be active (`src/mod_manager_ui.cpp:131-139`).
2. **Collision semantics differ by type.** There is no single "override" rule (§1.3). Traps that Part B will hit:
   - `vehicle_group`, `vehicle_placement`, `vehicle_spawn` are **append-only** (`src/vehicle_group.cpp:80-87,105-113,186-204`).
     You cannot remove US cars from dda groups in JSON. Even `aftershock_exoplanet` gets this wrong.
   - `monstergroup` **extends** unless `"override": true` (`src/mongroup.cpp:468-472`).
   - `talk_topic` **appends responses** (`src/npctalk.cpp:9403-9421`).
   - `npc` is **first-definition-wins**, so a mod redefinition is silently ignored (`src/npc.cpp:346,540`).
   - `item_group` is **replaced** unless `copy-from` names the same id (`src/item_factory.cpp:5131-5146`).
   - `mapgen` is **additive per om_terrain** (`src/mapgen.cpp:821-829`).
   - `palette` is **replaced** (`src/mapgen.cpp:4321`).
   - All `generic_factory` types are **replaced**, or patched in place by `copy-from` of the same id (`src/generic_factory.h:250-255,392-409`).
3. **The most scalable suppression tool for US overmap content** is `region_settings.feature_flag_settings.whitelist`.
   It filters every overmap special (`src/overmap.cpp:259-292`) **and every map extra** (`src/map_extras.cpp:1314-1319`)
   that lacks the flag. City building pools are replaced wholesale through `region_settings_city` (`src/regional_settings.cpp:572-585`).
   Precedents: `aftershock_exoplanet`, `hunvre`.
4. **The plan's type names are wrong at this SHA.** `COMESTIBLE`, `BOOK`, `TOOL`, `ARMOR` and `GENERIC` are **not registered
   types**. Only `"type": "ITEM"` is (`src/init.cpp:367`), and slots are chosen by `"subtypes": [ "COMESTIBLE" ]`
   (`src/item_factory.cpp:3115-3190`). `doc/MODDING.md:274-293` documents a `region_overlay` type that **does not exist**
   in the loader.
5. **Minimal C++ for Pass 1: one required seam, two strongly recommended** (§4.3):
   - (C1) `vehicle_group` `"override"` plus weight-0 removal. This is required for de-Americanized traffic, because dda road
     nested mapgen spawns `city_vehicles`, `city_pileup` and `police_pileup`.
   - (C2) Make `--check-mods` fail on a hard `JsonError`. Today it exits 0 (§6.2).
   - (C3) Add `vi` to the language list. This can wait for the vi pass.

### 1.2 `generic_factory<T>` inheritance (most types) [V]

`src/generic_factory.h`:
- `handle_inheritance` (`:245-287`). With `"copy-from": X`, it first looks up **real loaded objects**
  (`map.find`, `:250-255`), then `abstracts` (`:256-260`). If X is not found yet, the JSON object is pushed to `deferred`
  and loaded later (`:262-266`). `"abstract"` together with `"id"` throws (`:271-275`). Abstracts are stored in `abstracts`
  (`:283`) and cleared at finalize (`:420`).
- `load` (`:310-385`) supports `"id"` as a string or an array.
- `insert` (`:392-414`) **replaces** an existing object with the same id (`result = obj`, `:403`).
  `mod_tracker::check_duplicate_entries` throws `mod_error` only when the **same source (mod)** defines an id twice
  (`src/mod_tracker.h:75-82`).
- `finalize` (`:418-431`) calls `DynamicDataLoader::load_deferred` (`src/init.cpp:186-218`). That function iterates until no
  progress is made, then discards the leftovers with the misleading message "JSON contains circular dependency" (`:205-211`).
  In practice this usually means a **typo in `copy-from`**.
- Member-level modifiers:
  - `relative` / `proportional` for scalars (`:797-900`).
  - `extend` / `delete` for containers read through a `generic_typed_reader` (`:1568-1603`). A plain member **replaces**
    the container (`:1574-1577`). `extend`/`delete` apply only when `was_loaded`, i.e. with copy-from (`:1578-1583`).
  - `doc/JSON/JSON_INHERITANCE.md:196-203` says the same: not every type supports every modifier.

**Idiom: in-place patch of a dda object.** Use the same `id` plus `"copy-from"` of that id. Because copy-from resolves
against real objects first (`generic_factory.h:250`), this copies the dda object and then applies your fields. In-repo:
`data/mods/desert_region/region_settings/region_settings/desert_regional_map_settings.json:599-601`
(`"type":"region_settings","id":"default","copy-from":"default"`).

### 1.4 Cross-mod load order

- Mods load in `active_mod_order` order (`src/game_io.cpp:544-560`). The UI puts dependencies first (`src/mod_manager_ui.cpp:141-165`).
  Because saigon_2000s depends only on `dda`, it loads after dda, so every replace/patch in §1.3 lands on top of dda.
- `mod_interactions/` always loads after all mods (`src/game_io.cpp:562-569`, `doc/MOD_COMPATIBILITY.md:31,39`).
- **In `--check-mods` the order is different** (§6.2). Dependencies are loaded from a `std::set<mod_id>` (`src/game_io.cpp:192-195`),
  and `string_id::operator<` compares interned indices, which is "not the same order after process restart"
  (`src/string_id.h:230-236`). This is harmless for a mod whose only dependency is dda.

**≥ 2,426 is a lower bound**. On top of these, `data/core/*.json` (external options, weather types, help, tips) is always

### 3.2 Conclusion: depend on dda and override

- A standalone core (`"core": true`) would need re-implementations of ≥2,426 ids plus everything those objects reference
  (requirements, materials, qualities, body parts...). The mod UI allows only one core (`src/mod_manager_ui.cpp:131-139`),
  so no other mod could be combined with it. This is not viable.
- **Decision: `"dependencies": ["dda"]`, `"category": "total_conversion"`.** Keep every hardcoded id **valid**. Reskin
  where the setting needs it by patching the id in place (`"id": X, "copy-from": X`). Suppress spawning with blacklists,
  the region whitelist and pool replacement, never by deletion.
- **Never blacklist a hardcoded id.** An item blacklist also strips the id from every requirement
  (`src/item_factory.cpp:1700-1703`). A monster blacklist blocks even C++-initiated spawns (`src/creature_tracker.cpp:93`).
- Precedents confirm this: `aftershock_exoplanet`, `hunvre`, `Megacity` and `MA` all declare `"dependencies": ["dda"]` with
  `"category": "total_conversion"` (their `modinfo.json`).

### 4.2 Recommended architecture

**Thin C++ fork plus a fat JSON total-conversion mod, both kept in-repo.**

1. **`data/mods/saigon_2000s/`** holds ≈100% of setting content. Upstream never edits this path, so merging upstream causes
   **zero textual conflicts** in it.
2. **C++ patches** are few, each under ~30 lines, each behind a new optional JSON key whose default preserves upstream
   behaviour, and each with a unit test. The conflict surface when merging upstream is then a handful of hunks
   (`vehicle_group.cpp`, `game_io.cpp`, `options.cpp`).
3. **Semantic drift is the real maintenance cost**, not textual conflicts. Upstream renames and obsoletes dda ids that the
   mod references through copy-from, blacklists and pools. These show up as debugmsgs at load:
   - `"item on blacklist %s does not exist"` (`src/item_factory.cpp:1692`)
   - `"monster on blacklist %s does not exist"` (`src/mongroup.cpp:425-428`)
   - "circular dependency" for a dangling copy-from (`src/init.cpp:205-211`)
   - "Overmap special id %s has been migrated" (`src/overmap_special.cpp:94-101`)

   **Process:** merge upstream on a fixed cadence (e.g. weekly), then run `--check-mods saigon_2000s` plus
   `cata_test --mods=dda,saigon_2000s`. With C2 in place, CI fails fast. (The "dozens of PRs/day" upstream rate is from the
   brief and is UNVERIFIED here.)
4. **Why in-repo (`data/mods`) rather than a user mod dir:**
   - `lang/update_pot.sh:42-45` extracts `-i data/mods` recursively, so the mod's strings enter the main POT for free.
   - Mod `.mo` files are scanned **only** under `PATH_INFO::user_moddir()` (`src/translation_manager_impl.cpp:55-63`), so
     an in-repo mod must ship through the main catalogue anyway.
   - CI's `get_all_mods.py` automatically tests total conversions in isolation (`build-scripts/get_all_mods.py:21-23,73-74`).

### 6.2 `--check-mods`

- CLI: `--check-mods [mod…]` sets `test_mode = true` (`src/main.cpp:315-329`). It loads options (`:777-780`), then runs
  `g->check_mod_data(mods)` and exits with `check_mod_data(...) && !debug_has_error_been_observed() ? 0 : 1`

- Flow (`src/game_io.cpp:127-211`), per mod:
  - Build a fresh test world (`:166-170`).
  - Check dependencies (`:177-183`).
  - `load_core_data()` (`:187`), then dependencies (`:191-195`), then the mod via **`load_data_from_dir`** (`:198`).
  - `finalize_loaded_data()`, including all 79 consistency checks (`:199`).
- Gotchas [V]:
  1. **A hard JSON error exits 0.** The exception is caught and printed as "Error loading data" (`:200-202`), and the
     function still returns true (`:210`). Grep stderr for `Error loading data` until C2 lands.
  2. It uses `load_data_from_path` (`src/init.cpp:523-551`), which **does not exclude `mod_interactions/`**, unlike real
     world loading (`:566-567`). Keep Pass 1 free of `mod_interactions/` to avoid false errors.
  3. `conflicts` is not checked. Dependency order is set-ordered (§1.4).
  4. Unknown or misspelled keys produce "unvisited member" errors (`src/flexbuffer_json.cpp:249-275`), which do flip the

- Command: `./cataclysm-tiles --check-mods saigon_2000s 2>&1 | tee check.log; grep -E "Error loading data|DEBUG" check.log`
  (runtime UNVERIFIED; no binary yet).

## 7. Performance: load time, finalize passes, O(n²) spots, memory

Baseline volume [V, by grep of `data/json`]:
- 3,308 files, 51 MB.
- 10,440 `ITEM`, 7,072 `mapgen`, 5,603 `recipe`, 5,528 `item_group`, 3,325 `talk_topic`, 1,221 `MONSTER`,
  1,282 `overmap_terrain`, 514 `palette`, 727 `snippet`.

A Pass 1 mod adds hundreds of objects, **<2% of the object count**. Linear passes are not a concern.

| Hotspot | Complexity | Evidence | Impact for Saigon |
|---|---|---|---|
| `ITEM_BLACKLIST` finalize | O(B × (G_nodes + Reqs + Recipes)): for each blacklisted item, walk every item group (`remove_item`), every requirement (`blacklist_item`) and every recipe/uncraft map (`delete_if`) | `src/item_factory.cpp:1689-1709`; `src/recipe_dictionary.cpp:63-73,923-927`; `src/requirements.cpp:1258-1262` | With B≈300 US items: ~300 × (5.5k groups + reqs + ~7k recipes) ≈ 4×10⁶ node visits, probably sub-second (UNVERIFIED). **Whitelist mode** turns B into ~10k and is ~30× worse, and hits the UB at `:1670-1674`. **Rule: blacklist mode only.** |
| Nested-recipe audit | O(R_nested × R × k) | `src/recipe_dictionary.cpp:830-847` | Only for recipes with `subcategory: "CSC_*_NESTED"`. Keep TC nested recipes few. |
| `load_deferred` | O(n × chain depth) per factory; each pass rescans the remaining list | `src/init.cpp:186-218` | Negligible. BFS file order (`src/filesystem.cpp:356-361`) means a parent in a sub-folder defers its children one pass. |
| Mapgen setup | Every mapgen JSON (dda's 7k plus ours) is set up at finalize, even if the region never places it | `src/mapgen.cpp:716-750` (`oter_mapgen.setup()` `:718`) | This is the dominant fixed cost of depending on dda. We cannot avoid it without C++ (lazy setup), and it is unchanged by us. |
| Overmap special budget check | Σ min occurrences ≤ (OMAPX/OMSPEC_FREQ)² = (180/15)² = 144 | `src/overmap_special.cpp:72-91`, `src/map_scale_constants.h:37`, `src/omdata.h:693` | The check counts **all** specials, including dda ones filtered out by the whitelist. dda contributes ≈13 (python sum over `data/json`, ignoring copy-from, approximate). ~130 headroom for the TC. |
| Runtime blacklist checks | `item_is_blacklisted` is a set lookup (`src/item_factory.cpp:280-283`). `monster_is_blacklisted` does linear scans of category/species lists plus `obj()` per monster add (`src/mongroup.cpp:383-416`, `src/creature_tracker.cpp:93`) | Keep monster lists **short** (categories/species, not hundreds of ids) because this sits on the spawn path. |
| `generic_factory::insert` | O(1) amortized. `inc_version` invalidates string_id caches, which are rebuilt at finalize | `src/generic_factory.h:392-431` | none |
| JSON parse and memory | Files are parsed to flexbuffers, cached on disk as `.fb`, and **mmap'd** | `src/flexbuffer_cache.cpp:149-158,243-254`; `src/json_loader.cpp:95-124` | Warm loads avoid a reparse. Mapgen keeps `JsonObject`s alive, so mmap pages stay mapped. RSS impact of +hundreds of objects is negligible (UNVERIFIED numbers). |

Measurement plan (actionable):
- Per-pack load time is already logged at D_WARNING in `debug.log` (`src/game_io.cpp:556-559`, `src/perf.h:28-31`).
- Compare a world with `dda` alone against `dda,saigon_2000s`.

### 8.2 Ordered steps with validation (one commit each)

   `--mods=dda,saigon_2000s`.

   Validate:
   - debug overmap reveal shows no dda specials or extras;
   - the start location is found. This needs the start OMT to be placed by a city pool or a flagged special with

5. **B5/B7 items, books, recipes.** Use `"type":"ITEM"` + `subtypes`. Validate: `--check-mods` plus

6. **B9 monsters, groups, NPCs.** Rules: new npc ids; `"override": true` on redefined groups; keep all hardcoded

7. **C1 vehicle_group override** (C++ + test), then **B6** vehicles and groups. Override dda road groups `city_vehicles`,

9. After each step, run the formatter (§6.1) and `cata_test --mods=dda,saigon_2000s "[force_load_game]"`.

### 8.3 Cheap high-leverage idioms

- **Books:** same-id patch of dda recipe books (`"id":"cookbook_daintydishes","copy-from":"cookbook_daintydishes","name":…,"variants":[…]`).
  All dda `book_learn` references then teach from the Vietnamese-flavoured book with no recipe edits. `book_learn` has no
  `extend` (`src/recipe.cpp:472-481`), so the alternative would be re-declaring hundreds of recipes. New mechanics still
  belong in new books and recipes (critic rule: no pure name swaps).
- **Hardcoded groups:** replace the contents of `forage_*`, `default_zombie_clothes` and `everyday_corpse` (§3.1). This
  localizes foraging, zombie clothing and corpse loot globally at once.
- **Names:** snippet category override as hunvre does. It survives language reloads, unlike editing `data/names/*.json`,
  which is re-read by `reload_names` on language change (`src/text_snippets.cpp:97-126,186-193`, `src/translations.cpp:105`).
