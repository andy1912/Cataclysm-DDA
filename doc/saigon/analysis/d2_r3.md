## 0. Executive summary

1. **The city generator is a small, fully hardcoded recursive "plus-sign" street grower.** It lives in `src/overmap_city.cpp`, `place_cities` through `build_city_street`.
   - JSON controls only:
     - city size and spacing;
     - three weighted building pools (`houses`/`shops`/`parks`);
     - two radius/sigma pairs;
     - the connection id used for streets.
   - C++ fixes the street topology:
     - 4 arms from the centre (`src/overmap_city.cpp:228-230`);
     - a side street every `block_width + 1` OMT (3, or 4–6; `src/overmap_city.cpp:407`, `src/overmap_city.cpp:413`);
     - a 75 % chance to build per frontage (`src/overmap_city.cpp:36`, `src/overmap_city.cpp:439-444`);
     - orientation "front faces the street" (`src/overmap_city.cpp:284-285`).
2. **Overmap-scale structure can be expressed today, in JSON only, through three independent routes:**
   - (a) region + city pools of Saigon `city_building`s;
   - (b) large fixed or mutable `overmap_special`s ("district specials");
   - (c) **pre-generated overmap files** via the `OVERMAP_PREGENERATED_PATH` external option (`src/overmap.cpp:929-952`). The Massachusetts mod `data/mods/MA/` already ships 1,337 real-geography overmaps this way.
   - Route (c) is the only JSON-only way to get *authentic* non-grid Saigon topology: streets, canals and the river taken from OSM.
   - Limit of route (c): the loader reads **one z-level per file, chosen by the object's `z`**. Only the first array element is read (`src/savegame.cpp:893-903`).
3. **OMT-scale Vietnamese forms are well supported in JSON today:**
   - nhà ống rows (6 × 4-tile lots per OMT). Each row building has a shared roof walk that is continuous within the building and capped at its ends. Cross-building roof links need the small C++ seam C1 (§4.a.2).
   - Hẻm labyrinths, the chợ, and the motorbike frontage.
   - The key mechanisms are `place_nested` with `check_z`/`neighbors`/`joins` conditions, and `omt_stack`/`omt`-scoped mapgen parameters (`src/mapgen.cpp:1848-1858`). Desert Region already uses them (`data/mods/desert_region/mapgen/earth.json:295-331`).
4. **Pass-2 C++ seams:**
   - `overmap::build_cities()` (`src/overmap_city.cpp:214`) becomes a dispatch on a new `region_settings_city` key;
   - a new `overmap::place_canals()` runs between `polish_river` and `place_cities` (`src/overmap.cpp:985-991`);
   - `lay_out_street`'s river veto (`src/overmap_city.cpp:318`) gets a bridge-aware relaxation;
   - `pick_random_building_to_place` (`src/overmap_city.cpp:235`) generalises to N density rings;
   - a new built-in mapgen for alley-first block subdivision is registered in the table at `src/mapgen_functions.cpp:82-94`.
5. **Performance.** Tall stacks and vehicles are the main risks. All magnitudes are UNVERIFIED (§6.4).
   - Every OMT column is generated for all 21 z-levels in one call (`src/mapgen.cpp:226`).
   - Uniform levels skip `draw_map` (`src/mapgen.cpp:200-202`, `src/mapgen.cpp:239`, `src/mapgen.cpp:265`). They still pay a fixed per-level overhead (§6.2).
   - Each nested chunk re-scans the whole z-level for regional pseudo-terrain (`src/mapgen.cpp:6289` → `src/mapgen_functions.cpp:2238-2259`).
   - Every spawned vehicle rebuilds all vehicle caches (`src/mapgen.cpp:6917`).
   - Every vehicle in the bubble is processed by `map::vehmove` (`src/map.cpp:922-953`) and by `map::do_vehicle_caching` (`src/map.cpp:10784-10800`) each turn.
   - Tall buildings raise the sunlight-cache start level (`src/lightmap.cpp:371`).
6. **Bugs and traps found** (details in §2.5 and Risks):
   - `city_spacing` validation emits a debugmsg and then writes to `city_size` (`src/regional_settings.cpp:806-810`);
   - predefined cities can be duplicated (`src/overmap_city.cpp:204`);
   - the building pick can loop forever if no pool entry fits the city size (`src/overmap_city.cpp:268-277`);
   - a partial `"connections"` override silently nulls the other connection ids (`src/regional_settings.cpp:464-472` + `src/generic_factory.h:958-960`);
   - same-id mapgen from a mod is *added* to vanilla's weighted list, not substituted (`src/mapgen.cpp:648`, `src/mapgen.cpp:836`);
   - the pregen loader mishandles obsolete ids (`src/savegame.cpp:924-927`);
   - a vehicle that overlaps impassable terrain at mapgen **destroys that terrain and is smashed** (`src/mapgen.cpp:7065-7085`).

### 1.2 Region selection (per overmap)

Region is chosen when each overmap is constructed:

1. `overmap::overmap( const point_abs_om &p )` (`src/overmap.cpp:249-251`) sets `settings = overmap_buffer.get_overmap_region(...)`.
2. `overmapbuffer::get_overmap_region` (`src/overmap_worldgen.cpp:171-178`) asks the current dimension's `dimension_region_layout` generator.
3. That generator is one of four kinds:
   - `UNIFORM`/`RANDOM`/`ANGLES` are dynamic (`src/overmap_worldgen.cpp:108-146`, `src/overmap_worldgen.cpp:164-169`);
   - `MANUAL_VORONOI` is static, with a lazily built Voronoi map (`src/overmap_worldgen.cpp:114-125`, `src/overmap_worldgen.cpp:148-162`).
4. The default layout is `UNIFORM` → region `"default"` (`data/json/region_settings/region_settings/dimensions/dimension_regions.json:2-6`).

### 1.4 Runtime OMT → submap mapgen

`map::generate` (`src/mapgen.cpp:170`) builds one OMT column, meaning all 21 z-levels, in one call:

1. It allocates the canvas. Uniform OMTs (those whose `oter_type` has `uniform_terrain`, `src/omdata.h:447,651-656`, e.g. `open_air`, `solid_earth`) are filled cheaply with `set_all_ter` (`src/mapgen.cpp:200-202`).
2. It loops z from top to bottom (`src/mapgen.cpp:226`). This order lets upper overlays written by lower-level mapgen (`place_nested` with `"z": 1`) be merged (`src/mapgen.cpp:239`, `src/mapgen.cpp:276`).
3. It computes monster density from a 7×7 OMT neighbourhood (`src/mapgen.cpp:249-253`).
4. It builds a `mapgendata` (`src/mapgen.cpp:263`) and calls `draw_map` (`src/mapgen.cpp:266` → `src/mapgen.cpp:6545`) → `run_mapgen_func` (`src/mapgen.cpp:7834`) → the weighted pick in `mapgen_factory::generate` (`src/mapgen.cpp:651-657`) → `mapgen_function_json::generate` (`src/mapgen.cpp:6297`).
5. That function:
   - resolves any predecessor (`src/mapgen.cpp:6305-6325`);
   - applies rotation (`src/mapgen.cpp:6341-6346`);
   - applies `fill_ter`;
   - calls `apply_mapgen_in_phases` (`src/mapgen.cpp:6254`), which walks `jmapgen_objects::apply` (`src/mapgen.cpp:6403`);
   - handles nested chunks through `jmapgen_nested::apply` (`src/mapgen.cpp:3843-3868`) → `mapgen_function_json_nested::nest` (`src/mapgen.cpp:6380-6392`), which is itself `apply_mapgen_in_phases`;
   - finishes with `resolve_regional_terrain_and_furniture` (`src/mapgen.cpp:6289`).
6. Map extras run from the region collection (`src/mapgen.cpp:289-301`), then static spawns, then post-process generators (riot damage for city roads is `src/mapgen.cpp:355`).
7. `saven` stores the new submaps (`src/mapgen.cpp:400`) through `MAPBUFFER.add_submap` (`src/mapbuffer.cpp:81`).

`mapgendata` exposes the following to JSON conditions:

- the 8 horizontal neighbours `t_nesw` (`src/mapgendata.h:128`), plus above and below (`src/mapgendata.h:139`);
- mutable-special `joins` (`src/mapgendata.h:142`) and `predecessors_` (`src/mapgendata.h:125`);
- the `region` (`src/mapgendata.h:144`).

Neighbours are **rotated into the OMT's local frame** unless `IGNORE_ROTATION_FOR_ADJACENCY` is set (`src/mapgendata.cpp:80-84`, joins `src/mapgendata.cpp:118-119`). So a rotated building can always test "north" = street side.

Persistence:

- overmaps save `layers`, `cities`, `city_tiles`, `connections_out`, `joins_used` and more (`src/savegame.cpp:1341`, `src/savegame.cpp:1400-1416`, `src/savegame.cpp:1438`; load `src/savegame.cpp:559-606`, `src/savegame.cpp:803`);
- submaps go to `MAPBUFFER` and are never regenerated.

Consequence: changes to worldgen affect only overmaps that have not been generated yet, and changes to mapgen affect only OMTs that have not been visited yet.

### 3.2 The three override patterns in the precedent mods

1. **In-place overlay of the `default` ids** (`copy-from` the same id, then change fields):
   - TropiCataclysm: `data/mods/TropiCataclysm/region_settings/tropical_regional_map_settings.json:2-43` (river, ocean, forest, weather) and `data/mods/TropiCataclysm/region_settings/tropical_regional_map_settings.json:44+` (34 `region_terrain_furniture` remaps);

   - railroads: `data/mods/railroads/region_overlay.json` (uses `extend` on `houses`).
   - This is an **overlay**: unspecified fields come from vanilla. Pool keys *replace* unless you use `extend`.
2. **New region, new layout:** Megacity defines `region_settings` `mega_mega_city` (copy-from default, nulls rivers/ocean/forests/lakes/highways, `"cities": "mega_mega_city_settings"`). It then *overrides* `dimension_region_layout` `default` to `UNIFORM` → `mega_mega_city` (`data/mods/Megacity/modinfo.json:13-24`, `data/mods/Megacity/modinfo.json:37-66`).
   - It also defines a `dimension` `"Default"` with a capital D (`data/mods/Megacity/modinfo.json:13-17`), while vanilla's is `"default"` (`data/json/region_settings/region_settings/dimensions/dimensions.json:2-5`). The layout override is what takes effect. **UNVERIFIED** whether `"Default"` is dead data.
3. **Pre-generated overmaps:**
   - MA sets `OVERMAP_PREGENERATED_PATH = "MA/MA_overmap"` (`data/mods/MA/game_balance.json:8-12`);
   - it ships `overmap_X_Y.omap.gz` files (1,337 files, 11 MB), 351 `city` objects (`data/mods/MA/cities.json`), and a region with rivers/lakes/ocean/ravines/forests/highways all `null` (`data/mods/MA/regional_map_settings.json`).
   - The format is `[{"type":"overmap","om_pos":[x,y],"z":0,"layers":[[oter_id,count],...]}]`, run-length encoded in row-major order (`src/savegame.cpp:886-948`).
   - Only the first array element is read (`src/savegame.cpp:894`), so each file holds **one z-level**. That level is chosen by the object's `"z"` member, which defaults to 0 (`src/savegame.cpp:898-903`, written to `layer[z + OVERMAP_DEPTH]` at `src/savegame.cpp:936`).
   - Lake and ocean points are post-processed into shore, surface, water cubes and bed (`src/savegame.cpp:952-1000`).
   - Missing files fall back to `OUTSIDE_DEFINED_OMAP_OMT` (`src/overmap.cpp:943-951`).
   - Generation then continues with the remaining enabled steps.

**Recommendation for saigon_2000s:** use pattern 1 for pass 1: `copy-from` `"default"` and keep the id `"default"`.

- Reason: `DEFAULT_REGION` (`src/regional_settings.h:29`) and the vanilla dimension layout both point at it. Every system then picks it up without touching dimensions, and other `"default"`-keyed JSON (map extras, `region_terrain_furniture` ids) stays resolvable.
- Keep a **new id** for the city object (`"cities": "saigon_city"`). Vanilla's `default` city pool stays intact for any code that references it, and the Saigon pool is not accidentally extended by other mods.
- Add pattern 3 later, for the core districts only (see §7 Option C).

## 4. Q4: Expressiveness today (JSON only) for Vietnamese urban forms

### 4.0 The mapgen toolbox (verified loaders)

- **`"om_terrain"`** can be:
  - a string;
  - a flat array, where one function is shared by several ids;
  - a **2D array**, which gives one mapgen spanning N×M OMTs, with rows 24·M characters wide and 24·N tall (`src/mapgen.cpp:866-895`, precedent `data/json/mapgen/LIXA_mapgen.json:4`).
- **Weights are additive per id.** Every `"type":"mapgen"` for an id is appended to that id's weighted list (`src/mapgen.cpp:647-649`); nested ones are too (`src/mapgen.cpp:836-839`). A mod *cannot* remove vanilla variants for an id; it can only outweigh them (`"weight"` is `dbl_or_var`, default 1000, `src/mapgen.cpp:798-805`). **Use new Saigon oter ids** rather than re-skinning vanilla ones.
- **Top-level keys** (`src/mapgen.cpp:4524-4548`): `fill_ter`, `rows`, `palettes`, `terrain`, `furniture`, `rotation`, `predecessor_mapgen`, `fallback_predecessor_mapgen`, `flags` (`src/mapgen.cpp:4656`), `parameters`.
- **`place_*` arrays** (`src/mapgen.cpp:4755-4783`): `place_nested`, `place_vehicles`, `place_items`, `place_loot`, `place_monsters`, `place_terrain`, `place_furniture`, `place_zones`, `place_graffiti`, `place_signs`, `place_fields`, `place_ter_furn_transforms`, `place_variables`, `faction_owner`, and others.
- **Placement** `x`, `y`, `z`, `repeat` accept ranges (`src/mapgen.cpp:1222-1228`). The `z` offset lets a ground-floor mapgen write into upper floors (precedent `data/json/mapgen/cave.json:29`). `doc/JSON/MAPGEN.md:295-303` confirms positive z offsets are fully supported.
- **Nested chunks**: `"nested_mapgen_id"` + `"mapgensize"`.
  - The size must be **square** (`src/mapgen.cpp:4554-4561`).
  - Row characters `" "`/`"."` without definitions are no-ops inside nests (`src/mapgen.cpp:4724`, with the fallback-terrain rule at `src/mapgen.cpp:4570`).
  - **Nested rotation is not applied.** `rotation` is parsed (`src/mapgen.cpp:4566`), but `nest()` has it commented out as a TODO (`src/mapgen.cpp:6383-6384`). Orientation variants must be authored per direction, or rely on the whole OMT's rotation.
- **`place_nested` conditions** (`src/mapgen.cpp:3792-3798`, test at `src/mapgen.cpp:3834-3838`; doc `doc/JSON/MAPGEN.md:1197-1247`):
  - `chunks` / `else_chunks`: weighted lists of *mapgen values*, so `{ "param": ... }` and `{ "switch": ..., "cases": ... }` both work (`src/mapgen.cpp:1648-1657`). A `switch` must list a case for every possible value, or a debugmsg fires (`src/mapgen.cpp:1566-1571`). The case `"null"` is a valid nested id (`src/mapgen.cpp:677-681`);
  - `neighbors` (oter id or prefix/type match, 8 directions + above/below);
  - `joins` (mutable-special joins);
  - `flags` / `flags_any` (oter flags such as `SIDEWALK`, `RIVER`);
  - `predecessors`;
  - `check_z` (absolute z list).
- **Parameters** have `scope` ∈ {`overmap_special`, `omt`, `omt_stack`, `nest`} (`src/mapgen_parameter.h:12-21`, loader `src/mapgen.cpp:1762-1764`).
  - **`omt_stack`** values are chosen once per x,y column and stored on the overmap (`src/mapgen.cpp:1848-1858` → `src/overmap.cpp:759-787`).
  - So every floor of a building sees the same choice. Precedent: `data/mods/desert_region/mapgen/earth.json:295-331`.
- **Palettes** are flattened into the mapgen at load time (`mapgen_palette::add`, `src/mapgen.cpp:4348-4420`, called from `setup_common`, `src/mapgen.cpp:4680`). A palette with a *choice* becomes a hidden `overmap_special`-scoped parameter (`src/mapgen.cpp:4365-4369`). Runtime cost is therefore a per-piece constraint check, not a palette lookup.

- Multi-OMT footprints along +x follow the vanilla `strip_mall` precedent (`data/json/overmap/multitile_city_buildings.json:5201-5215`).
- Special rotation is applied to the whole footprint: points go through `om_direction::rotate` (`src/overmap.cpp:3012`) and each oter through `get_rotated( dir )` (`src/overmap_special_fixed.cpp:269`). So **the relative rotation of cells inside one building is fixed at authoring time**, whatever the street direction.
- `sg_nhaong_pair_1x2` fills a whole thin block (block width 2, `src/overmap_city.cpp:407`).
  - In a 3–5-deep block its back cell faces the block interior, so its frontage faces field.
  - Mitigation: give it a pool weight low enough that the 1×N rows dominate. The rate is **UNVERIFIED**; B1 counts `pair_1x2` cells whose back frontage abuts a non-road.
- One mapgen function can serve several oter ids. With a flat `om_terrain` array the first function is added for every listed id (`src/mapgen.cpp:878-891`).
  - The role types therefore share their z0–z2 and z4–z5 mapgens.
  - Only the z3 mapgen differs per role, and only in caps and links.
  - This keeps the JSON cost low: 6 role types (`solo`, `endw`, `mid`, `ende`, `pairf`, `pairb`) × 6 levels = 36 oter ids, but only 5 shared functions (z0–z2, z4, z5) + 5 z3 functions (`solo`, `endw`, `mid`, `ende`, and `pair`, which is shared by `pairf`/`pairb`).
- The z0 oters `copy-from` `generic_city_building` (`data/json/overmap/overmap_terrain/overmap_terrain.json:51`), which adds `SIDEWALK`. Upper oters use `generic_city_building_roof` (`data/json/overmap/overmap_terrain/overmap_terrain.json:57`), which also deletes `riot_damage` (`data/json/overmap/overmap_terrain/overmap_terrain.json:55-60`).
  - Only z0 is riot-post-processed.
  - Its `bash_damage` (intensity up to 60, `data/json/post_process_generators.json:7`) can hit shutters and parked bikes at generation time. This is intended wear.
  - `SIDEWALK` is what makes adjacent road OMTs draw sidewalks (`data/json/mapgen/road.json:194-199`).

#### 4.a.2 Rooftop connectivity (canon: "Rooftops connect for movement", `doc/saigon/CONTENT_BIBLE.md:29`)

**Why r2's rule was wrong (critic D1).**

- A `PREFIX` neighbour match compares id strings (`is_ot_prefix`, `src/overmap_terrain.cpp:310-331`), so `sg_nh_mid_z3_east` matches exactly like `_north`.
- `mapgendata` rotates only the neighbour *position* (`overmap_buffer.ter( over + displace( dir ).rotate( rotation ) )`, `src/mapgendata.cpp:80-84`), never the id.
- `neighbor_oter_check::test` then calls `is_ot_match` on that absolute id (`src/mapgen.cpp:3604-3621`).
- A shared rotatable mapgen therefore **cannot distinguish a same-rotation neighbour from a perpendicular one**. r2's neighbour-conditioned caps and planks could leave walk-off drops at perpendicular corners, and could build half-planks.

**Rule R-ROOF (r3).** Continuity is determined by **role type**, never by a neighbour test.

1. **Shared base roof at z = 3.** Every lot has ≥ 3 storeys, so rows 16–19 of every cell are a walkable **roof walk** at z3.
   - It uses `t_concrete_roof` (move_cost 2, FLAT, ROAD, no INDOORS; `data/json/furniture_and_terrain/terrain-roofs.json:286-294`).
   - Lot dividers are `t_railing` on lx = 0, rows 16 and 19 only. It is passable at move_cost 3 (`data/json/furniture_and_terrain/terrain-fences-gates.json:1186-1191`).
   - The rear edge (row 19) is a `t_railing` line along x = 0..23, broken only by the plank gap in back-to-back roles.
2. **Unconditional end caps by role.** The z3 mapgen of each role places `t_concrete_wall` (`data/json/furniture_and_terrain/terrain-walls.json:228`) on rows 16–19:
   - `sg_nh_solo`, `sg_nh_pairf` and `sg_nh_pairb`: at x = 0 and x = 23;
   - `sg_nh_endw`: at x = 0;
   - `sg_nh_ende`: at x = 23;
   - `sg_nh_mid`: none.
   - No neighbour test is involved, so **no walk tile can ever border a building's outside without a wall**. Inside one building, the endw/mid/ende cells abut in their fixed relative rotation, so the walk is continuous across the whole building: up to 72 tiles for `sg_nhaong_row_3`.
3. **Plank link only inside a back-to-back building.** `sg_nhaong_pair_1x2` places its plank unconditionally.
   - `t_bridge` (`data/json/furniture_and_terrain/terrain-bridges-docks.json:4-11`) runs at x = 11–12 over local rows 19–23 of *both* cells, with `t_railing` at x = 10 and x = 13.
   - The two halves meet because the second cell is authored as the 180° counterpart: x ↦ 23 − x maps {11, 12} onto itself.
   - `t_bridge` has no bash entry, so collapse by bashing is not a concern for the plank itself. The `SUPPORTS_ROOF`/`COLLAPSES` counting (`src/map.cpp:4172-4185`) remains **UNVERIFIED** for the walk tiles next to it. The test's bash step checks it.
4. **Height steps.**
   - **h3:** a full deck at z3 over rows 2–19. The stair arrives at (2, 13) as `t_stairs_down`. That tile carries `INDOORS` (`data/json/furniture_and_terrain/terrain-zlevel-transitions.json:120-128`). It is a deliberate single-tile exception to "roof decks carry no INDOORS" (critic D10), and harmless (one sheltered tile).
   - **h4:** a setback room at z3 over rows 2–15, floored with `t_thconc_floor` (INDOORS, `"roof": "t_concrete_roof"`; `data/json/furniture_and_terrain/terrain-floors-indoor.json:4-11`). A door at (1, 15) opens onto the walk. The z4 roof deck is reached by the stair column.
   - **h5:** one more setback storey (z4), with the roof deck at z5.
   - No lot top is more than 2 storeys above the walk, and every step has stairs. `t_ladder_up`/`t_ladder_down` (`data/json/furniture_and_terrain/terrain-zlevel-transitions.json:185-211`) are an allowed cheaper substitute.
5. **Across separate buildings** (procedural city):
   - **JSON-only pass 1:** walks of *different* buildings do **not** connect. Each ends in a wall.
     - This is a documented downgrade of r2's claim.
     - Canon is met within a building (≤ 72 tiles), inside back-to-back pairs, and throughout the authored district special (§7.2, where every cell's role is known).
     - It is not met across arbitrary city buildings.
   - **Pass-1 minimal C++ seam C1 (recommended):** a rotation-aware neighbour predicate, which makes cross-building links possible. See §5.1 and §8 P1-C1.
     - Extend `neighbor_oter_check` (`src/mapgen.cpp:3569-3621`) with an optional per-entry `"relative_rotation": 0..3`.
     - The test becomes `( dat.neighbor_at( dir )->get_rotation() - dat.terrain_type()->get_rotation() + 4 ) % 4 == rel` in addition to the id match. `oter_t::get_rotation` is at `src/overmap_terrain.cpp:851-863`; `mapgendata::neighbor_at` is at `src/mapgendata.cpp:286`.
     - With C1, end caps become `else_chunks` of `{ "om_terrain": "sg_nh", "om_terrain_match_type": "PREFIX", "relative_rotation": 0 }` on the west and east sides. The 4-row walk then continues between same-street buildings. Perpendicular neighbours still get the wall, because their relative rotation is 1 or 3.
6. **Rooftop water (critic D9).** Every lot has one `f_standing_tank` (LIQUIDCONT, keg-style, `keg_capacity` 300 L; `data/json/furniture_and_terrain/furniture-storage.json:1316-1328`) on its highest deck.
   - h3: at (3, 18) on the z3 deck. h4/h5: at (3, 3) on the top roof.
   - It is filled through the palette `"liquids"` mapping (loader key at `src/mapgen.cpp:4499`), following the precedent `data/json/mapgen/cs_gardening_allotment.json:71-76` (`"liquids": { "O": { "liquid": "water", "amount": [ 0, 100 ] } }`). Its loader is `jmapgen_liquid_item` (`src/mapgen.cpp:2342-2382`), which adds the liquid as charges on the tile, and the keg-style container holds it.
   - Rate: 1 tank per lot, 6 per OMT, each with `amount` [40, 200] charges. The volume per charge of `water` is **UNVERIFIED**; tune it in game so tanks hold roughly 10–60 % of capacity.
   - Water is untreated. Boiling is gameplay (A4).
   - Rain refilling is **not** designed here; it is deferred to A3.

**Validation: test `saigon_rooftop_walkability`** (new, `tests/saigon_mapgen_test.cpp`; run with `--mods=saigon_2000s`, `tests/test_main.cpp:368-370`). For 20 seeds (`rng_set_engine_seed`, as at `tests/mapgen_post_process_test.cpp:175`):

### 4.b Hẻm alleys 1–3 tiles wide, dead-ends, labyrinths

**Within an OMT: yes.** Use a **rotation-symmetric spine plus quadrants**. This replaces r1's independent Wang quadrants, which could disagree across a shared edge (critic D3).

- **Spine.** Two 2-tile-wide alleys cross the OMT: x = 11–12 over all y, and y = 11–12 over all x. They form four **arms** (N, E, S, W) that meet at the centre.
  - The arm ends are the only OMT-edge **ports**: (11–12, 0), (23, 11–12), (11–12, 23) and (0, 11–12).
  - This port set is invariant under 90° rotation, so rotated neighbours always line up. Neighbours are rotated into the local frame at `src/mapgendata.cpp:80-84`.
  - `rotate` can therefore stay `true`.
- **Quadrants.** The four 11×11 areas beside the spine each get one nested chunk, picked by weighted `chunks`.
  - Each variant holds tiny homes, altars and café plots, reached by 1-tile sub-alleys with dead-end spurs.
  - **Authoring rule (tested):** every variant must open onto *both* spine arms that border it.
  - Nested chunks cannot rotate (`src/mapgen.cpp:6383-6384`), so variants are authored per quadrant position (`_nw`, `_ne`, `_sw`, `_se`).
- **Dead-ends at OMT scale.**
  - One `omt`-scoped parameter, `closed_arm`, takes values {`none` ×3, `n`, `e`, `s`, `w`}. Parameter scopes are defined at `src/mapgen_parameter.h:12-21`.
  - Each arm has one "block" placement whose chunk is a `switch` on `closed_arm` (`src/mapgen.cpp:1535-1571`, `src/mapgen.cpp:1648-1657`). The switch yields the wall-and-house chunk only for its own letter and `"null"` for every other value.
  - Because one parameter drives all four placements, **at most one arm is ever closed**. The four quadrants stay connected through the remaining three arms and the centre.
- **Edge ports (r3: no rotation-blind row matching; critic D1 and D8).**
  - A port stays open when the neighbour in that direction is one of these:
    - another hẻm OMT (`sg_hem` PREFIX);
    - a road (`road` TYPE);
    - a canal cell (`sg_kenh` PREFIX), whose 2-tile embankment walk runs along both banks at local y = 0–1 and y = 22–23 (§4.d).
  - In both the hẻm and the canal cases the neighbour's port-facing edge is traversable in **every** rotation.
    - The hẻm's centred ports are rotation-invariant.
    - A canal cell met side-on presents its embankment walk.
    - A canal cell met end-on presents its channel. The channel is wadeable `t_water_murky` (move_cost 5, `SHALLOW_WATER`, no `DEEP_WATER`; `data/json/furniture_and_terrain/terrain-liquids.json:79-86`), which connects to both embankments.
  - **Rows are not in the JSON-only list.**
    - A PREFIX match on `sg_nh` cannot tell whether the row presents its rear strip or its party-wall side. The reasons are `src/overmap_terrain.cpp:310-331` and `src/mapgendata.cpp:80-84`.
    - Toward rows the port is therefore capped (`else_chunks` → `sg_hem_cap_*`). A hẻm next to rows is reached through the adjoining road or hẻm cells.
    - Separately, the row's own rear strip (§4.a.1) is open at both of its OMT ends, so it can feed a hẻm or road at its side.
  - **With C1 (§4.a.2 item 5):** add `{ "om_terrain": "sg_nh", "om_terrain_match_type": "PREFIX", "relative_rotation": d }`. Here d is 0 for the north port, 1 for east, 2 for south and 3 for west.
    - Derivation: a row at absolute direction r_hem + d presents its rear (absolute r_row + 2) back toward the hẻm exactly when r_row = r_hem + d.
    - Only rear-facing rows then open a port.

    ```jsonc
    "neighbors": { "north": [ { "om_terrain": "sg_hem",  "om_terrain_match_type": "PREFIX" },
                              { "om_terrain": "road",    "om_terrain_match_type": "TYPE" },
                              { "om_terrain": "sg_kenh", "om_terrain_match_type": "PREFIX" } ] }
    ```

    - Match types are at `src/enums.h:149-165`.
    - The check class is at `src/mapgen.cpp:3569-3621`.
    - `neighbors` lists use OR semantics within a direction (`src/mapgen.cpp:3610-3616`).
  - Otherwise `else_chunks` caps the arm end with a wall (`sg_hem_cap_n`, and so on).
  - An arm whose port is open is never closed by `closed_arm`. Each arm's block placement carries the same `neighbors` condition, with `"null"` in `chunks` and the switch-driven block in `else_chunks`:

  ```jsonc
  { "chunks": [ "null" ],
    "else_chunks": [ { "switch": { "param": "closed_arm", "fallback": "none" },
                       "cases": { "none": "null", "n": "sg_hem_arm_block_n", "e": "null", "s": "null", "w": "null" } } ],
    "x": 11, "y": 0,
    "neighbors": { "north": [ { "om_terrain": "sg_hem",  "om_terrain_match_type": "PREFIX" },
                              { "om_terrain": "road",    "om_terrain_match_type": "TYPE" },
                              { "om_terrain": "sg_kenh", "om_terrain_match_type": "PREFIX" } ] } }
  ```

  - A `switch` must list every possible value, or a debugmsg fires (`src/mapgen.cpp:1566-1571`). `"null"` is a valid nested id (`src/mapgen.cpp:677-681`).
- **Why connectivity is guaranteed inside the OMT.**
  - Each quadrant touches two arms, and at most one arm is closed. Every arm reaches the centre.
  - Every open port is therefore reachable from every plot door, provided each quadrant variant connects its plots to both of its arms. That authoring rule is tested.
  - Reachability *from outside* needs at least one open port. That is a placement property, checked at district level (§7.2 test).
- **Validation: test `saigon_hem_connectivity`** (in `tests/saigon_mapgen_test.cpp`).
  - Run 100 seeds × 4 rotations (`sg_hem_block_{north,east,south,west}`). Set neighbours with `overmap_buffer.ter_set`, in 4 configurations: all hẻm, all road, all canal, and all rows (so all ports are capped in JSON-only mode).
  - Generate with `smallmap::generate`.
  - BFS over z0 tiles that are passable, **or** whose terrain is openable. Doors such as `t_door_c` have move_cost 0 but define an `open` target (loader `src/mapdata.cpp:1378`). The BFS treats `ter.open` as a traversable edge (critic D4b).
  - Assert:
    - all open ports and all plot doors inside the quadrants are reachable;
    - each port tile is open exactly when its neighbour satisfies the condition;
    - in the all-rows configuration, no port tile is open.
  - For the all-hẻm case, also generate a 2×1 pair and assert that the shared port tiles are open on both sides.

**Across OMTs (block-scale labyrinth): yes, with a mutable `overmap_special`.**

- `joins` define alley connectivity between OMTs. Join-conditioned `place_nested` (`"joins": { "north": [ "hem_to_hem" ] }`) opens the matching edge port. Joins used are persisted (`src/savegame.cpp:803`) and fed to mapgen (`src/mapgendata.cpp:118-119`).
- Precedent for narrow meandering linear growth: `data/json/overmap/overmap_mutable/stream.json:12-47`.
- Caveats:
  - mutable placement ignores `must_be_unexplored` (TODO at `src/overmap_special_mutable.cpp:780`);
  - failed growth leaves "unresolved joins" debugmsgs (`src/overmap_special_mutable.cpp:866-890`). Always include closing pieces with `max` in a final phase (doc `doc/JSON/OVERMAP.md:1000-1018`).
- **UNVERIFIED:** using a *mutable* special as a `city_building` pool entry. The loader allows it (`src/overmap_special.cpp:322-336` is not gated by type), and the placement path is generic (`src/overmap_city.cpp:292-294`), but no vanilla city building does it. None of the 414 `city_building` objects in `data/json` are mutable.
  - Validate by adding one to the pool and running the `[overmap]` tests with `--mods=saigon_2000s`.

**Alley-first subdivision at block scale is *not* possible JSON-only.** The city builder decides frontage first (§2.3). Block interiors deeper than 2 OMT remain `field`. They are only *marked* as city by `flood_fill_city_tiles` (`src/overmap_city.cpp:516-559`); they are not built on. JSON workarounds, in order of preference:

1. Deep city buildings with footprint `(0,0)` frontage row plus `(0,1)` hẻm-block. These fill the 3–5-deep blocks when they fit, within 10 retries (`src/overmap_city.cpp:289`).
2. Infill `overmap_special`s with `"city_distance": [-1, 0]` and `"locations": ["field"]`.
   - `min = -1` is required: the check is `min < dist`, and dist is 0 inside the radius (`src/overmap_special.cpp:214-216`, `src/overmap_city.cpp:500-514`). A max of 0 is legal (`src/common_types.h:39-50`).
   - Density is capped by sector sampling: at most one special per 15×15 sector across both passes (`src/overmap.cpp:3215-3225`, `src/overmap.cpp:3338`), i.e. ≤ 144 per overmap.
3. Map-level only: a high-weight `field` mapgen variant that draws squatter or hẻm housing when a `SIDEWALK` neighbour exists (`flags_any`), else plain field.
   - This fixes the look on the ground, but the overmap still shows "field". Mark it cosmetic.

### 4.c Chợ (wet market), large multi-OMT

- **Fixed special, 2×2 or 3×3.** One 2D-`om_terrain` mapgen covers the hall (48×48 or 72×72 rows); a z = 1 roof stack sits above it.
- Stall grid: 4×4 or 6×6 nested slots, each a parameter-selected stall type, following the precedent `data/json/mapgen/cs_market_small.json:45-48`. Stall types are fish tanks, meat hooks, vegetables and dry goods, with `place_loot`/`place_items` per stall.
- Placement choices:
  - As a `shops` pool entry with `"flags": ["CITY_UNIQUE"]` and `"city_sizes": [8, -1]`, so it lands near the centre (`shop_radius`). A 2×2+ footprint only fits the 3–5-wide blocks. Expect frequent failure (10 retries, `src/overmap_city.cpp:289`), and **keep a non-unique fallback in the pool** (B3).
  - As an `overmap_special` with `occurrences`, `city_distance: [1, 4]` and `connections` to `local_road`. The road is then auto-built toward the city centre (`src/overmap_special_fixed.cpp:305-319`), which gives the classic "market at the edge of the grid".
- Street spill-over (chợ tự phát on the adjacent road) cannot be driven by the market's own mapgen, because it does not own the road OMT. Options:
  - put a 2-row frontage strip inside the market OMTs; or
  - add a region `map_extra_collection` for the `road` extras key (map extras are applied per OMT, `src/mapgen.cpp:284-303`). This is not location-aware.

### 4.d Canals (kênh/rạch) through the city

- **The river generator cannot make narrow canals.**
  - Major rivers: `river_scale = 1 + std::max( 1, river_scale )` (`src/overmap_water.cpp:555`) gives radius ≥ 2. They are drawn with `points_in_radius_circ` (`src/overmap_water.cpp:163`), so they are at least ~5 OMT (~120 m) wide.
  - Branches are placed with `river_scale - river_branch_scale_decrease` (`src/overmap_water.cpp:212-213`). They can reach radius 1, which is ~3 OMT (~72 m) wide. A radius of 0 is rejected (`src/overmap_water.cpp:55-57`).
  - Both follow random Bézier paths (`src/overmap_water.cpp:69-110`).
  - So even the narrowest river branch is 2–7× wider than a 10–30 m kênh.
- **Streets refuse water** (`src/overmap_city.cpp:318`), and cities are built *after* rivers (`src/overmap.cpp:966` versus `src/overmap.cpp:991-997`). Any water present first cuts the grid, with no bridges.
- **overmap_connection reuse (UNVERIFIED, fragile):**
  - A `canal` connection with a LINEAR water oter could be drawn by a special's `connections` entry. `build_connection` supports any linear type (`src/overmap.cpp:2559-2644`).
  - But specials are placed after cities (`src/overmap.cpp:1018`). The path targets the *city centre* (`src/overmap_special_fixed.cpp:312-317`). The greedy path is rejected wherever the connection has no subtype for that terrain (`src/overmap.cpp:2508-2512`).
  - Crossing streets needs a bridge subtype on `road` locations, which would *replace* road line-oters and break intersections.
  - Not recommended for pass 1.
- **Works today (pass 1):**
  - Canals authored *inside* district specials (§7) as dedicated oters: `sg_kenh_ew` and `sg_kenh_causeway_ns`.
  - **Water model:**
    - The channel is 6–8 tiles of `t_water_murky`, which is `SHALLOW_WATER`, `SWIMMABLE`, `FISHABLE` and not `DEEP_WATER` (`data/json/furniture_and_terrain/terrain-liquids.json:79-86`). It fits "polluted canal, water unsafe until boiled" (`doc/saigon/CONTENT_BIBLE.md:32`).
    - The canal exists at z0 only. The levels below keep the region default (`solid_earth`/rock, which are uniform).
    - Deep variants (`t_water_dp` / `t_water_moving_dp`) carry `DEEP_WATER` and `EMPTY_SPACE` (`data/json/furniture_and_terrain/terrain-liquids.json:41-48`, `data/json/furniture_and_terrain/terrain-liquids.json:155-162`). They would need water or bed OMTs at z−1, the way lakes do (`src/savegame.cpp:972-978`). They are therefore avoided in pass 1.
  - Banks are 2-tile embankment walks (`t_sidewalk`) plus stilt houses (`sg_kenh_stilt_*`) on the canal-facing side.
  - **Crossing:**
    - `sg_kenh_causeway_ns` is a z0 street deck (`t_pavement`) with a culvert: the water terminates on both sides of the deck. This is a deliberate simplification.
    - Vanilla road bridges put the deck at **z1** (`bridge_road`, created by `overmap::generate_over`, `src/overmap.cpp:1146-1195`), with supports below (`src/overmap.cpp:1170-1180`). A z1 canal bridge is deferred to P2.3.
  - **Canon gaps, deferred explicitly:**
    - *Boat routes*: boats need `FLOATS` parts to spawn on deep water (`src/mapgen.cpp:6940`, `src/mapgen.cpp:6953`). Navigation on a shallow, dead-ended canal is not designed in pass 1. This is owned by domain A3 (boats) plus P2.3 (a canal network connected to the river).
    - *Boat presence* (canon "small boats", `doc/saigon/CONTENT_BIBLE.md:32`) **is** met in pass 1, as static vehicles.
      - `add_vehicle_to_map` rejects non-floating vehicles only on `DEEP_WATER` (`src/mapgen.cpp:6953`), so a boat can sit on `t_water_murky`.
      - `sg_kenh_ew` places at most 1 `canoe` (`data/json/vehicles/boats.json:4-12`; parts at x = −1..2, a 4-tile hull) per cell. It is parked parallel to the channel at `rotation: 0`, mounted at (10, y_mid) with `chance: 30`.
      - The slot lies wholly on water tiles and far from both embankments, so neither the merge branch (`src/mapgen.cpp:6964-7060`) nor the impassable branch (`src/mapgen.cpp:7065-7085`) can trigger.
      - This counts toward the §6.3 vehicle budget.
    - *Wet-season floods*: no mapgen or worldgen support is designed here. This is owned by A3 (weather) and needs a flood mechanic.
  - **Optional placement variant (canal meets river):**
    - Add a second copy of the district special whose canal-mouth cell, the east end of the canal row, gets a per-terrain `locations` entry. Per-terrain `locations` are supported (`src/overmap_special.cpp:150-158`), and the location is the existing `water` overmap_location (`data/json/overmap/special_locations.json:59-63`). Vanilla precedent: "Riverside Dwelling" pins a `river_north` cell with `"locations": [ "water" ]` (`data/json/overmap/overmap_special/specials.json:106-111`).
    - That copy can only be placed where the mouth overwrites a river bank.
    - Placement success is **UNVERIFIED**, because rivers are random. Keep the landlocked special as the mandatory fallback.
  - Narrow in-OMT water modelled on the vanilla `stream` mapgen (`data/json/mapgen/stream.json`, a 2–3 tile channel), placed by a mutable wilderness special (`data/json/overmap/overmap_mutable/stream.json`), for rural rạch outside the city.

- Three failure modes follow:
  1. **Vehicle overlaps vehicle.** The two are merged into a wreck and both are smashed (`src/mapgen.cpp:6964-7060`). A 200-part cap applies (`src/mapgen.cpp:6971-6975`).
  2. **Vehicle overlaps impassable terrain.** The terrain is destroyed with `destroy( p, true )`, then the vehicle is `smash()`ed (`src/mapgen.cpp:7065-7085`). A bike parked into a shutter demolishes the shop front.
  3. **Origin out of bounds.** The origin is rejected (`src/mapgen.cpp:6877-6881`). A merge target out of bounds raises a debugmsg (`src/mapgen.cpp:7002-7010`). The load-time checker flags placements that can leave 0..23 (`src/mapgen.cpp:2787-2825`).
- Phase ordering: vehicles (phase `default_`) are placed before nested props (phase `nested_mapgen`), per `src/mapgen.h:89-99`. So a prop can end up *under* a vehicle only if the slot geometry overlaps. The design below has no overlap.

## 5. Q5: What needs C++ for authentic topology (pass 2)

Design constraint: at OMT scale the network is **4-connected**. Road oters are LINEAR with 16 line variants (`oter_flags::line_drawing`, `src/omdata.h:293`; `build_connection` uses `om_lines`, `src/overmap.cpp:2586-2640`). "Organic" at overmap scale therefore means:

- irregular spacing, T-junctions, dead-ends, non-rectangular blocks, arterials that zig-zag, and river/canal crossings.

It does not mean diagonals. Diagonal or curved *appearance* belongs to mapgen: a road OMT can draw a diagonal inside itself using neighbour conditions (`road_curved` precedent in `data/json/mapgen/road.json:101-107`).

### 5.2 Determinism and savegame compatibility

- **Determinism contract.** `tests/overmap_test.cpp:1043-1109` asserts identical overmaps from the same RNG engine state.
  - The new code must draw only from `rng_get_engine()`, in a fixed order.
  - Do not iterate `unordered_*` containers while drawing random numbers. `city_tiles` is an `unordered_set`, so sort before use.
  - Noise layers already use `g->get_seed()` and are stateless (`src/overmap_noise.cpp:13-43`). Prefer them for spatial fields such as a density or "old-town" mask.
- **Mapgen C++ (hẻm): scope of the local engine.**
  - The *topology decisions* use a local engine seeded by `hash( g->get_seed(), tripoint_abs_omt )`. These are the edge-port hash and the maze carving. Adjacent OMTs and revisits therefore agree regardless of visiting order.
  - *Interior dressing* may keep using the global RNG, because it is delegated to JSON nested chunks, which draw from the global stream (e.g. `x_in_y` in `jmapgen_vehicle::apply`, `src/mapgen.cpp:2742`). Examples are furniture variants, items and the chunk picks inside a plot.
  - Only topology must be order-independent. Dressing variation between runs is acceptable, just as it is for vanilla mapgen.
- **Save compatibility:**
  - Already-generated overmaps and submaps are loaded, not regenerated (`src/overmap.cpp:3695-3735`; `MAPBUFFER`).
  - New serialized fields must be optional on load. The loader dispatches by member name (`src/savegame.cpp:555-610`), and older saves simply lack the new member.
  - Renamed Saigon oters need `oter_id_migration` entries (`src/overmap.cpp:1332-1347`, applied `src/overmap.cpp:1382-1397`).
  - Changing `layout` on an existing world only affects overmaps generated afterwards. Document this in the mod as "new world recommended".

## 6. Q6: Performance

**Status of the numbers.** No build existed when this analysis was done, so nothing here was measured.

- Every numeric magnitude in this section is **UNVERIFIED**: op counts, vehicle counts, level counts and multipliers. They are derived from reading the code.
- Each figure is tagged with the benchmark in §6.4 that confirms or refutes it.
- The comparison baseline in every case is a **vanilla downtown** (§6.4 B0).

### 6.1 Overmap generation (single thread, on demand, can hitch mid-walk)

Cost drivers per new overmap:

- **Layer scans.**
  - `place_specials` scans up to 21×180×180 = 680,400 OMTs for lake and ocean presence (`src/overmap.cpp:3245-3259`).
  - `generate_sub` always walks every z from −1 downward; see the comment at `src/overmap.cpp:1057`, "This forces every sub level to generate".
  - That is 10 × 32,400 cells with **three** `ter_unsafe` reads each: `oter_id_here`, `oter_above` and `oter_ground` (`src/overmap.cpp:1080-1083`, loop `src/overmap.cpp:1077-1116`).
  - These scans are identical for vanilla and Saigon, so they are not a delta.
- **City building.**
  - Each frontage spot costs up to 10 × (weighted pick + `can_place_special` over the footprint) (`src/overmap_city.cpp:289-303`).
  - Specials with an `eoc` run a dialogue condition on every test (`src/overmap.cpp:2981-2986`). **Avoid `eoc` on city buildings.**
  - `lay_out_street` probes a 3×3 neighbourhood per step (`src/overmap_city.cpp:324`).
  - Megacity notes that cost grows with size (`src/overmap_city.cpp:157-158`).
  - Saigon's 1×1 row buildings do not add placement work beyond vanilla's. Cost is bounded by street length.
  - Large footprints (the chợ) raise the retry rate. The magnitude is **UNVERIFIED**; see B1.
- **Road network.** `connect_closest_points` builds O(n²) edges (`src/overmap.cpp:2672-2680`), with one greedy path per accepted edge (`src/overmap.cpp:2726`).
- **Specials.**
  - 144 sectors × ≤ 10 attempts, each reshuffling the enabled list (`src/overmap.cpp:3158`, `src/overmap.cpp:3213-3228`).
  - Large mutable specials resolve joins per piece (`src/overmap_special_mutable.cpp:843-870`).
  - **Failed mandatory specials cascade into generating a neighbouring overmap** (`src/overmap.cpp:3356-3381`). Keep Saigon mandatory specials few and easy to place.
- **Hidden trigger from runtime mapgen.**
  - `map::generate` samples `overmap_buffer.ter` over ±3 OMT for monster density (`src/mapgen.cpp:249-253`).
  - `mapgendata` reads its neighbours through `overmap_buffer.ter` (`src/mapgendata.cpp:84`).
  - Both go through `overmapbuffer::get` (`src/overmapbuffer.cpp:889-893` → `src/overmapbuffer.cpp:100-121`), which **generates the neighbouring overmap if it is missing**. A walk near an overmap border therefore stalls once for a full generation.

### 6.2 Mapgen per OMT column

**Fixed per-column overhead (paid by every column, uniform or not).** For each of the 21 levels (`src/mapgen.cpp:226`):

- 4 submaps are allocated (`src/mapgen.cpp:187-211`).
- The 7×7 density loop runs, costing 49 `overmap_buffer.ter` calls (`src/mapgen.cpp:249-253`). That is **1,029 calls per column**.
- A `mapgendata` is constructed (`src/mapgen.cpp:263`).
- Map-extras lookup, static-spawn roll and post-process dispatch run (`src/mapgen.cpp:283-379`).
- Every newly generated submap is saved (`src/mapgen.cpp:392-406`).
- Uniform levels are cheap only in that they skip `draw_map` (`src/mapgen.cpp:200-202`, `src/mapgen.cpp:239`, `src/mapgen.cpp:265`).
- This overhead is the same for vanilla and Saigon columns. **It is the floor that B2 must subtract.**

**Variable cost (non-uniform levels only).**

- Every non-uniform level runs the full JSON function (`src/mapgen.cpp:266` → `src/mapgen.cpp:6297`).
- Riot-damage post-process is the default for `generic_city_building` (`data/json/overmap/overmap_terrain/overmap_terrain.json:47`).
- A z0..z5 nhà ống stack has 6 non-uniform levels. Two points of comparison:
  - A vanilla 2-storey house with basement and roof (`2storyModern01`, `data/json/overmap/multitile_city_buildings.json:4-11`) has 4.
  - Vanilla downtown already contains taller stacks: `office_skyscraper` up to z = 9 (`data/json/overmap/multitile_city_buildings.json:3643`, pool weight 300 in `data/json/region_settings/region_settings/regional_map_settings.json:801`) and `apartments_con_new` up to z = 7 (`data/json/overmap/multitile_city_buildings.json:2376`).
  - Expected per-column cost is therefore **within vanilla-downtown range**, not 6× a bungalow. **UNVERIFIED; see B2.**

**Nested chunks.**

- Each `nest()` runs `apply_mapgen_in_phases` (`src/mapgen.cpp:6380-6392`).
- That call ends with `resolve_regional_terrain_and_furniture` over the whole z-level (`src/mapgen.cpp:6289` → `src/mapgen_functions.cpp:2238-2259`). It visits the 24×24 smallmap level and does 2 flag tests per tile.
- **Vehicle-collision pre-pass (critic D6).**
  - Every `apply_mapgen_in_phases` call, including each `nest()`, first runs `objects.has_vehicle_collision( md, offset )`, even when `verify` is false (`src/mapgen.cpp:6259`).
  - `jmapgen_objects::has_vehicle_collision` visits every object and calls `veh_at` for vehicle-sensitive pieces (`src/mapgen.cpp:6436-6452`, `src/mapgen.cpp:1883-1893`).
  - For `place_nested`, it recurses into **every entry** of the selected list, and every function of each entry (`src/mapgen.cpp:3941-3961`), evaluating each entry's param/switch.
  - A lot → sub-chunk tree is therefore walked once per ancestor, in addition to its real application.
  - It also evaluates `where.x.get()` / `where.y.get()` (`src/mapgen.cpp:6444-6447`), which draw from the global RNG for ranged coordinates. This is a further reason why §5.2 limits the order-independence guarantee to C++-driven topology.
- **Nest estimate for the §4.a design.**
  - About 12 nests per level (6 lots × lot + sub-chunk).
  - z0 adds `sg_frontage_row` plus its 6 prop placements (≈ 4 non-null).
  - z3 adds the role cap and plank chunks (1–3).
  - So ≈ 12–18 nests per level. Each does a regional-resolve scan (≈ 576 × 2 flag tests) plus the recursive pre-pass: ≈ 14–21k flag tests per level and ≈ 90–120k per 6-level stack.
  - **UNVERIFIED; see B2.** B2 reports ms per column. It also reports a design-time **nest count per column**, computed statically from the JSON by a script that walks `place_nested` trees. A runtime nest counter would need an instrumentation hook in `mapgen_function_json_nested::nest` (`src/mapgen.cpp:6380`), listed as optional seam I1 in §5.1.
- **Keep nesting depth ≤ 2, and never nest per tile.** The palette `"nested"` per-character mapping in `data/mods/desert_region/mapgen/earth.json:333-338` does nest per tile.
- There is no recursion-depth guard: grepping `src/mapgen.cpp` for depth or recursion limits found none.

**Vehicles.**

- A vehicle forces terrain resolution earlier (`src/mapgen.cpp:6419-6425`).
- `add_vehicle` runs `init_state`, `place_spawn_items` and precalc (`src/mapgen.cpp:6890-6897`).
- It then calls `rebuild_vehicle_level_caches()` for every vehicle (`src/mapgen.cpp:6917` → `src/map.cpp:596-609`), which walks all vehicles on all 21 levels.
- With the §4.f cap of ≤ 6 vehicles per OMT this is O(36·parts) per column. That is expected to be negligible. **UNVERIFIED; see B2.**

**Items.**

- Shop loot (`place_items`/`place_loot` → `map::place_items`, `src/mapgen.cpp:6709`) is the main memory multiplier.
- Six shops per OMT means more street-level items than a vanilla one-shop OMT. The count delta is **UNVERIFIED; see B2**, which counts items per column.

### 6.3 Memory and per-turn costs

**Submap memory.**

- A non-uniform submap allocates a `maptile_soa` of 144 × {`ter_id`, `furn_id`, `lum`, `cata::colony<item>`, `field`, `trap_id`, `rad`} (`src/submap.h:62-69`, `ensure_nonuniform` at `src/submap.h:83-92`).
- Uniform submaps allocate nothing.
- A 6-level row OMT has 24 non-uniform submaps; a vanilla 4-level house has 16. Bytes per submap are **UNVERIFIED; see B3**, which records `sizeof( maptile_soa )` and resident memory.

**Per-turn caches.**

- `build_map_cache` loops every z for the outside, transparency and floor caches, gated by dirty flags (`src/map.cpp:10804-10815`).
- `loadn` dirties all z-levels whenever a submap is loaded (`src/map.cpp:9328-9335`).
- **`do_vehicle_caching( z )` runs for every z each time `build_map_cache` runs, with no dirty gate** (`src/map.cpp:10819-10821` → `src/map.cpp:10784-10800`). It walks every part of every vehicle.
- This is a second per-turn vehicle cost, on top of `vehmove`. It scales with total vehicle parts in the bubble.

**Sunlight.**

- The sunlight cache starts at `calc_max_populated_zlev() + 1` (`src/lightmap.cpp:371`). That value is the highest non-uniform level in the bubble (`src/map.cpp:11914-11947`).
- Levels above every obstacle take the `fully_outside` fast-fill path (`src/lightmap.cpp:409-413`).
- Vanilla downtown already reaches z = 7–9 (`office_skyscraper`, `apartments_con_new`, above). So a Saigon street of z = 3–5 roofs does **not** raise the start level relative to vanilla downtown. It raises the number of *partly obstructed* levels, which take the slow quadrant path, across more of the bubble.
- Magnitude **UNVERIFIED; see B3**, which times `build_sunlight_cache`.

**Vehicles per turn.**

- `map::vehmove` visits every vehicle on every level, then runs `vehproceed` up to 100 times (`src/map.cpp:922-953`).
- The bubble is about 5.5 × 5.5 OMT, roughly 30 OMTs.
- With the §4.f design (≤ 6 real vehicles per row OMT, mean 3) and ~15 frontage OMTs in view, the bubble holds **≈ 45 expected / 90 worst-case** Saigon vehicles, plus road vehicles.
- The budget is **≤ 150 vehicles in the bubble**. This covers both `vehmove` and `do_vehicle_caching`.
- r1's "~450 vehicles" scenario (30 real bikes per OMT) is the design that is rejected. It is kept only as B3's stress case.
- All counts are **UNVERIFIED; see B3.**
