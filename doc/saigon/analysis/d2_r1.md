## 0. Executive summary

1. **The city generator is a small, fully hardcoded recursive "plus-sign" street grower.** It lives in `src/overmap_city.cpp`, `place_cities` through `build_city_street`.
   - JSON controls only:
     - city size and spacing;
     - three weighted building pools (`houses`/`shops`/`parks`);
     - two radius/sigma pairs;
     - the connection id used for streets.
   - C++ fixes the street topology: 4 arms from the centre, side streets every 2 or 3–5 OMT, a 75 % chance to build per frontage, and orientation "front faces the street".
2. **Overmap-scale structure can be expressed today, in JSON only, through three independent routes:**
   - (a) region + city pools of Saigon `city_building`s;
   - (b) large fixed or mutable `overmap_special`s ("district specials");
   - (c) **pre-generated overmap files** via the `OVERMAP_PREGENERATED_PATH` external option (`src/overmap.cpp:929-952`). The Massachusetts mod `data/mods/MA/` already ships 1,337 real-geography overmaps this way.
   - Route (c) is the only JSON-only way to get *authentic* non-grid Saigon topology: streets, canals and the river taken from OSM. It works for z = 0 only.
3. **OMT-scale Vietnamese forms are well supported in JSON today:**
   - nhà ống rows (6 × 4-tile lots per OMT), hẻm labyrinths, the chợ, and the motorbike frontage.
   - The key mechanisms are `place_nested` with `check_z`/`neighbors`/`joins` conditions, and `omt_stack`-scoped mapgen parameters. The latter keep each lot's height consistent across z-levels (`src/mapgen.cpp:1848-1858`). Desert Region already uses them (`data/mods/desert_region/mapgen/earth.json:295-331`).
4. **Pass-2 C++ seams:**
   - `overmap::build_cities()` (`src/overmap_city.cpp:214`) becomes a dispatch on a new `region_settings_city` key;
   - a new `overmap::place_canals()` runs between `polish_river` and `place_cities` (`src/overmap.cpp:985-991`);
   - `lay_out_street`'s river veto (`src/overmap_city.cpp:318`) gets a bridge-aware relaxation;
   - `pick_random_building_to_place` (`src/overmap_city.cpp:235`) generalises to N density rings;
   - a new built-in mapgen for alley-first block subdivision is registered in the table at `src/mapgen_functions.cpp:82-94`.
5. **Performance.** Tall stacks and vehicles are the main risks.
   - Every OMT column is generated for all 21 z-levels in one call (`src/mapgen.cpp:226`). Only *uniform* levels are free (`:200-202`, `:239`, `:265`).
   - Each nested chunk re-scans the whole z-level for regional pseudo-terrain (`src/mapgen.cpp:6289` → `src/mapgen_functions.cpp:2238-2259`).
   - Every spawned vehicle rebuilds all vehicle caches (`src/mapgen.cpp:6917`).
   - Every vehicle in the bubble is processed each turn (`src/map.cpp:922-953`).
   - Tall buildings raise the sunlight-cache start level (`src/lightmap.cpp:371`).
6. **Bugs and traps found** (details in §2.5 and Risks):
   - `city_spacing` validation writes to `city_size` (`src/regional_settings.cpp:809`);
   - predefined cities can be duplicated (`src/overmap_city.cpp:204`);
   - the building pick can loop forever if no pool entry fits the city size (`src/overmap_city.cpp:268-277`);
   - a partial `"connections"` override silently nulls the other connection ids (`src/regional_settings.cpp:464-472` + `src/generic_factory.h:958-960`);
   - same-id mapgen from a mod is *added* to vanilla's weighted list, not substituted (`src/mapgen.cpp:648`, `:836`).

### 1.2 Region selection (per overmap)

Region is chosen when each overmap is constructed:

1. `overmap::overmap( const point_abs_om &p )` (`src/overmap.cpp:249-251`) sets `settings = overmap_buffer.get_overmap_region(...)`.
2. `overmapbuffer::get_overmap_region` (`src/overmap_worldgen.cpp:171-178`) asks the current dimension's `dimension_region_layout` generator.
3. That generator is one of four kinds:
   - `UNIFORM`/`RANDOM`/`ANGLES` are dynamic (`src/overmap_worldgen.cpp:108-146`, `164-169`);
   - `MANUAL_VORONOI` is static, with a lazily built Voronoi map (`:114-125`, `148-162`).
4. The default layout is `UNIFORM` → region `"default"` (`data/json/region_settings/region_settings/dimensions/dimension_regions.json:2-6`).

### 1.4 Runtime OMT → submap mapgen

`map::generate` (`src/mapgen.cpp:170`) builds one OMT column, meaning all 21 z-levels, in one call:

1. It allocates the canvas. Uniform OMTs (those whose `oter_type` has `uniform_terrain`, `src/omdata.h:447,651-656`, e.g. `open_air`, `solid_earth`) are filled cheaply with `set_all_ter` (`src/mapgen.cpp:200-202`).
2. It loops z from top to bottom (`src/mapgen.cpp:226`). This order lets upper overlays written by lower-level mapgen (`place_nested` with `"z": 1`) be merged (`:239`, `:276`).
3. It computes monster density from a 7×7 OMT neighbourhood (`:249-253`).
4. It builds a `mapgendata` (`:263`) and calls `draw_map` (`:266` → `:6545`) → `run_mapgen_func` (`:7834`) → the weighted pick in `mapgen_factory::generate` (`:651-657`) → `mapgen_function_json::generate` (`:6297`).
5. That function:
   - resolves any predecessor (`:6305-6325`);
   - applies rotation (`:6341-6346`);
   - applies `fill_ter`;
   - calls `apply_mapgen_in_phases` (`:6254`), which walks `jmapgen_objects::apply` (`:6403`);
   - handles nested chunks through `jmapgen_nested::apply` (`:3843-3868`) → `mapgen_function_json_nested::nest` (`:6380-6392`), which is itself `apply_mapgen_in_phases`;
   - finishes with `resolve_regional_terrain_and_furniture` (`:6289`).
6. Map extras run from the region collection (`:289-301`), then static spawns, then post-process generators (riot damage for city roads is `:355`).
7. `saven` stores the new submaps (`:400`) through `MAPBUFFER.add_submap` (`src/mapbuffer.cpp:81`).

`mapgendata` exposes the following to JSON conditions:

- the 8 horizontal neighbours `t_nesw` (`src/mapgendata.h:128`), plus above and below (`:139`);
- mutable-special `joins` (`:142`) and `predecessors_` (`:125`);
- the `region` (`:144`).

Neighbours are **rotated into the OMT's local frame** unless `IGNORE_ROTATION_FOR_ADJACENCY` is set (`src/mapgendata.cpp:80-84`, joins `:118-119`). So a rotated building can always test "north" = street side.

Persistence:

- overmaps save `layers`, `cities`, `city_tiles`, `connections_out`, `joins_used` and more (`src/savegame.cpp:1341`, `:1400-1416`, `:1438`; load `:559-606`, `:803`);
- submaps go to `MAPBUFFER` and are never regenerated.

Consequence: changes to worldgen affect only overmaps that have not been generated yet, and changes to mapgen affect only OMTs that have not been visited yet.

## 2. Q2: City and street algorithm, hardcoded versus JSON

### 2.1 Seeding (`overmap::place_cities`, `src/overmap_city.cpp:65-212`)

```cpp

const double city_map_coverage_ratio = 1.0 / std::pow( 2.0, op_city_spacing );          // :104 [H]

```

- **Random size distribution [H]** (`:173-185`): `rng(size-1, max)`, then 1/3 tiny (×1/3), 1/3 small (×2/3), 1/6 large (×3/2), 1/6 huge (×2), clamped to 2..55.
- **Candidates [H]** (`:127-131`): only OMTs equal to the region's z0 `default_oter` (normally `field`) inside radius `OMAPX/2 − max_city_size`. Points within radius 2 of a chosen seed are removed (`:190-196`).
- **The seed tile becomes `road_nesw` [H]** (`:198`, `:206`). For predetermined cities this overwrites *whatever* is at `pos` (`:206`), including a river.
- **Megacity [H]** (`:137-163`) places 5 fixed seeds of size 40 at quarter points.
- **Predetermined cities [J]**: `"type": "city"` with `pos_om` and `pos` (`src/city.cpp:72-82`, doc `doc/JSON/OVERMAP.md:1298-1328`). The random-size clamp is skipped in this branch; the size comes from JSON.

`lay_out_street` (`:306-382`) enforces these rules:

- **[H]** it stops at rivers, ravines and highways (`:318-319`), with the TODO "Make it so the city picks a bridge direction" at `:317`;
- **[H]** it refuses to run a street next to a third parallel road via the collision counter (`:324-335`). This counts only `oter_type_road` (`:34`, `:328`);
- **[J]** it may lay road only where the `intra_city_road_connection` has a subtype for that terrain (`:319`, `connection.pick_subtype_for`);
- **[H]** it crosses highways only perpendicularly (`:356-373`).

Every street is straight: `straight_path` (`:38-53`) builds it.

Result: a rectilinear plus-shaped fractal, with blocks 2 or 3–5 OMT deep between parallel side streets.

### 2.3 Building choice and orientation (`place_building` / `pick_random_building_to_place`)

```cpp
const tripoint_om_omt building_pos = p + om_direction::displace( dir );      // :284  one OMT off the street
const om_direction::type building_dir = om_direction::opposite( dir );      // :285  local "north" faces the street

for( size_t retries = 10; retries > 0; --retries ) { ... can_place_special ... place_special ... }  // :289-303 [H]
```

Pool choice (`:235-278`):

- `shop_normal = max(shop_radius, normal_roll(shop_radius, shop_sigma))`;
- if `shop_normal > town_dist` → `pick_shop`;
- else if `park_normal > town_dist` → `pick_park`;
- else → `pick_house` (`:248-264`).

This is a fixed **3-ring model** [H]. Only the radii and sigmas are [J]. The retry loop rejects the flags `CITY_UNIQUE`, `GLOBALLY_UNIQUE` and `OVERMAP_UNIQUE`, and also rejects any building whose `city_sizes` excludes the town size (`:268-277`).

How specials are oriented and rotated:

- A special's local frame has the street to the **north** of point (0,0). Rotation is `om_direction::rotate(elem.p, dir)` for placement (`src/overmap.cpp:3012`) and `elem.terrain->get_rotated(dir)` for the oter (`src/overmap_special_fixed.cpp:269`).
- Frontage-parallel footprints extend along +x; deep footprints extend along +y (away from the street). For `city_building`, x and y must be ≥ 0 (`doc/JSON/OVERMAP.md:1199`).
- **[H/J trap]** A `city_building` cannot declare `connections`. The loader reads `connections` only when `type == "overmap_special"` (`src/overmap_special.cpp:297`, `316-318`). `occurrences`, `city_distance` and `priority` are likewise special-only (`:343-347`). `city_sizes`, `flags` and `rotate` apply to both (`:341`, `:351-352`).
- Single-OMT oters can be listed directly in a pool. They are wrapped into specials by `overmap_specials::create_building_from` (`src/regional_settings.cpp:943-951`).

### 2.4 What JSON controls (the complete list, from the loaders)

`region_settings_city` (`src/regional_settings.cpp:572-585`, struct `src/regional_settings.h:52-103`) has these keys:

- `is_megacity`
- `city_size` (mandatory; clamped to 0..16 in `finalize`, `:801-805`)
- `city_spacing`
- `shop_radius`, `shop_sigma`, `park_radius`, `park_sigma`
- `name_snippet`
- `houses` / `shops` / `parks`: `[[special_or_oter_id, weight], ...]`. Giving the key *replaces* the list (`src/generic_factory.h:1576`). `"extend"`/`"delete"` modify it (`:1592-1600`), which is how `data/mods/railroads/region_overlay.json` adds a station.

`region_settings` (`src/regional_settings.cpp:610-642`) adds:

- `connections.intra_city_road_connection` and `inter_city_road_connection` (`:470-471`)
- `max_urbanity`, `urbanity_increase` (world-scale gradient, `src/overmap.cpp:2363-2422`)
- `place_roads`, `place_specials`, `feature_flag_settings` (special whitelist/blacklist, applied in `src/overmap.cpp:258-296`)

`city` objects fix city positions and sizes (`src/city.cpp:72-82`).

Street *shape* is **not** controllable from JSON.

### 3.2 The three override patterns in the precedent mods

1. **In-place overlay of the `default` ids** (`copy-from` the same id, then change fields):

   - railroads: `data/mods/railroads/region_overlay.json` (uses `extend` on `houses`).
   - This is an **overlay**: unspecified fields come from vanilla. Pool keys *replace* unless you use `extend`.
2. **New region, new layout:** Megacity defines `region_settings` `mega_mega_city` (copy-from default, nulls rivers/ocean/forests/lakes/highways, `"cities": "mega_mega_city_settings"`). 3. **Pre-generated overmaps:**
   - MA sets `OVERMAP_PREGENERATED_PATH = "MA/MA_overmap"` (`data/mods/MA/game_balance.json:8-12`);
   - it ships `overmap_X_Y.omap.gz` files (1,337 files, 11 MB), 56 `city` objects (`data/mods/MA/cities.json`), and a region with rivers/lakes/ocean/ravines/forests/highways all `null` (`data/mods/MA/regional_map_settings.json`).

   - Only the first object, and therefore **one z-level**, is read (`:894`, `:898-903`).
   - Lake and ocean points are post-processed into shore, surface, water cubes and bed (`:952-1000`).
   - Missing files fall back to `OUTSIDE_DEFINED_OMAP_OMT` (`src/overmap.cpp:943-951`).
   - Generation then continues with the remaining enabled steps.

**Recommendation for saigon_2000s:** use pattern 1 for pass 1: `copy-from` `"default"` and keep the id `"default"`.

- Reason: `DEFAULT_REGION` (`src/regional_settings.h:29`) and the vanilla dimension layout both point at it. Every system then picks it up without touching dimensions, and other `"default"`-keyed JSON (map extras, `region_terrain_furniture` ids) stays resolvable.
- Keep a **new id** for the city object (`"cities": "saigon_city"`). Vanilla's `default` city pool stays intact for any code that references it, and the Saigon pool is not accidentally extended by other mods.
- Add pattern 3 later, for the core districts only (see §7 Option C).

## 4. Q4: Expressiveness today (JSON only) for Vietnamese urban forms

### 4.0 The mapgen toolbox (verified loaders)

- **`"om_terrain"`** can be:
  - a string;
  - a flat array, where one function is shared by several ids;
  - a **2D array**, which gives one mapgen spanning N×M OMTs, with rows 24·M characters wide and 24·N tall (`src/mapgen.cpp:866-895`, precedent `data/json/mapgen/LIXA_mapgen.json:4`).
- **Weights are additive per id.** Every `"type":"mapgen"` for an id is appended to that id's weighted list (`src/mapgen.cpp:647-649`); nested ones are too (`:836-839`). A mod *cannot* remove vanilla variants for an id; it can only outweigh them (`"weight"` is `dbl_or_var`, default 1000, `:798-805`). **Use new Saigon oter ids** rather than re-skinning vanilla ones.
- **Top-level keys** (`src/mapgen.cpp:4524-4548`): `fill_ter`, `rows`, `palettes`, `terrain`, `furniture`, `rotation`, `predecessor_mapgen`, `fallback_predecessor_mapgen`, `flags` (`:4656`), `parameters`.
- **`place_*` arrays** (`src/mapgen.cpp:4755-4783`): `place_nested`, `place_vehicles`, `place_items`, `place_loot`, `place_monsters`, `place_terrain`, `place_furniture`, `place_zones`, `place_graffiti`, `place_signs`, `place_fields`, `place_ter_furn_transforms`, `place_variables`, `faction_owner`, and others.
- **Placement** `x`, `y`, `z`, `repeat` accept ranges (`src/mapgen.cpp:1222-1228`). The `z` offset lets a ground-floor mapgen write into upper floors (precedent `data/json/mapgen/cave.json:29`). `MAPGEN.md:295-303` confirms positive z offsets are fully supported.
- **Nested chunks**: `"nested_mapgen_id"` + `"mapgensize"`.
  - The size must be **square** (`src/mapgen.cpp:4554-4561`).
  - Row characters `" "`/`"."` without definitions are no-ops inside nests (`:4724`, with the fallback-terrain rule at `:4570`).
  - **Nested rotation is not applied.** `rotation` is parsed (`:4566`), but `nest()` has it commented out as a TODO (`:6383-6384`). Orientation variants must be authored per direction, or rely on the whole OMT's rotation.
- **`place_nested` conditions** (`src/mapgen.cpp:3792-3798`, test at `:3834-3838`; doc `doc/JSON/MAPGEN.md:1197-1247`):
  - `chunks` / `else_chunks`: weighted lists of *mapgen values*, so `{ "param": ... }` and `{ "switch": ..., "cases": ... }` both work (`:1648-1657`);
  - `neighbors` (oter id or prefix/type match, 8 directions + above/below);
  - `joins` (mutable-special joins);
  - `flags` / `flags_any` (oter flags such as `SIDEWALK`, `RIVER`);
  - `predecessors`;
  - `check_z` (absolute z list).
- **Parameters** have `scope` ∈ {`overmap_special`, `omt`, `omt_stack`, `nest`} (`src/mapgen_parameter.h:12-21`, loader `src/mapgen.cpp:1762-1764`).
  - **`omt_stack`** values are chosen once per x,y column and stored on the overmap (`src/mapgen.cpp:1848-1858` → `src/overmap.cpp:759-787`).
  - So every floor of a building sees the same choice. Precedent: `data/mods/desert_region/mapgen/earth.json:295-331`.
- **Palettes** are flattened into the mapgen at load time (`mapgen_palette::add`, `src/mapgen.cpp:4348-4420`, called from `setup_common`, `:4680`). A palette with a *choice* becomes a hidden `overmap_special`-scoped parameter (`:4365-4369`). Runtime cost is therefore a per-piece constraint check, not a palette lookup.

### 4.a Nhà ống shophouses (≈4 m × 15–25 m, 3–5 floors, open shop front, roof terrace)

**Geometry.** One OMT is 24×24 tiles. Six 4-tile lots fill the frontage exactly.

- Depth budget per OMT: rows 0–1 are a *vỉa hè* frontage strip for parking and stalls; rows 2–19 are the house (18 m deep); rows 20–23 are a rear service strip.
- With the vanilla block width of 2 (`src/overmap_city.cpp:407`), two rows stand back to back. Their rear strips then join into a ~6–8 tile **back hẻm** between them. This emerges from the block structure with no extra logic.

Overmap level: a 1×1 `city_building` stacked z = 0..5.

```jsonc
{ "type": "city_building", "id": "sg_nhaong_row_mixed", "locations": [ "land" ],
  "city_sizes": [ 2, -1 ],                                  // B3: must cover every city size → non-unique fallback
  "overmaps": [
    { "point": [ 0, 0, 0 ], "overmap": "sg_nhaong_row_z0_north" },
    { "point": [ 0, 0, 1 ], "overmap": "sg_nhaong_row_z1_north" },
    { "point": [ 0, 0, 2 ], "overmap": "sg_nhaong_row_z2_north" },
    { "point": [ 0, 0, 3 ], "overmap": "sg_nhaong_row_z3_north" },
    { "point": [ 0, 0, 4 ], "overmap": "sg_nhaong_row_z4_north" },
    { "point": [ 0, 0, 5 ], "overmap": "sg_nhaong_row_z5_north" } ] }
```

- The z0 oter should `copy-from` `generic_city_building` (`data/json/overmap/overmap_terrain/overmap_terrain.json:51`, which adds `SIDEWALK`). Upper oters should use `generic_city_building_roof` (`:57`). The `SIDEWALK` flag is what makes adjacent road OMTs draw sidewalks (`data/json/mapgen/road.json:194-199`) and city vehicles (`data/json/mapgen/nested/road_vehicles_nested.json:76-91`).

**Per-lot height consistency.** Six `omt_stack` parameters, each a `nested_mapgen_id`, all live in one palette shared by all six z-level mapgens:

```jsonc
{ "type": "palette", "id": "sg_nhaong_row_params",
  "parameters": {
    "lot0": { "type": "nested_mapgen_id", "scope": "omt_stack",
              "default": { "distribution": [ [ "sg_lot_pho_h3", 3 ], [ "sg_lot_pho_h4", 4 ], [ "sg_lot_cafe_h5", 1 ], [ "sg_lot_tiemvang_h4", 1 ] ] } },
    "lot1": { ... }, "lot2": { ... }, "lot3": { ... }, "lot4": { ... }, "lot5": { ... } } }
```

Every floor's mapgen is then identical apart from `om_terrain`:

```jsonc
{ "type": "mapgen", "om_terrain": "sg_nhaong_row_z2",
  "object": { "fill_ter": "t_open_air", "palettes": [ "sg_nhaong_row_params" ],
    "place_nested": [
      { "chunks": [ { "param": "lot0", "fallback": "sg_lot_pho_h3" } ], "x": 0,  "y": 0 },
      { "chunks": [ { "param": "lot1", "fallback": "sg_lot_pho_h3" } ], "x": 4,  "y": 0 },
      ... x = 8, 12, 16, 20 ] } }
```

Each lot chunk is a 24×24 nested mapgen that fills only columns 0–3. It switches content by absolute z through `check_z`, exactly as the `check_z` palette in `earth.json:333-338`:

```jsonc
{ "type": "mapgen", "nested_mapgen_id": "sg_lot_pho_h4",
  "object": { "mapgensize": [ 24, 24 ],
    "place_nested": [
      { "chunks": [ "sg_lot_ground_shop_pho" ], "x": 0, "y": 0, "check_z": [ 0 ] },
      { "chunks": [ [ "sg_lot_floor_family", 3 ], [ "sg_lot_floor_rental", 1 ] ], "x": 0, "y": 0, "check_z": [ 1, 2, 3 ] },
      { "chunks": [ [ "sg_lot_roof_terrace", 3 ], [ "sg_lot_roof_tank_altar", 1 ] ], "x": 0, "y": 0, "check_z": [ 4 ] } ] } }
```

- An `h3` lot simply puts its terrace at `check_z: [3]` and places nothing at z = 4..5.
- The **open shop front** is authored in the z0 ground chunk:
  - no wall on row 2; a roll-up shutter terrain across the 4-tile front instead (a new OPENCLOSE terrain pair; content work for A4);
  - stalls and tables spill into rows 0–1.
- **Stairs alignment** is guaranteed because the same lot chunk decides every floor.

Why this is structural, not an asset swap:

- It changes the *parcel grain* from 1 building per OMT to 6 independent buildings.
- It adds per-parcel vertical variation that stays consistent under z-streaming (omt_stack is stored on the overmap, so a later visit to z = 3 gets the same choice).
- It creates a rear alley network through block adjacency.

Options for upper z oters and their trade-off:

- A 6-level stack costs 6 non-uniform submap levels even where a lot is only 3 floors high (see §6).
- Alternative: `sg_nhaong_row_h3` / `_h4` / `_h5` variants with a uniform lot height per OMT, and per-lot variation only in detailing. This is cheaper, and the city pool weights set the skyline.

### 4.b Hẻm alleys 1–3 tiles wide, dead-ends, labyrinths

**Within an OMT: yes.** Use a **Wang-tile** construction.

- Split the OMT into four 12×12 quadrant slots.
- Each quadrant chunk variant fixes "ports" at the midpoints of its four edges (open or closed), and guarantees that its open ports are internally connected. This is authored per variant, with dead-end spurs inside.
- The OMT mapgen picks each quadrant by weighted `chunks`. That gives the random labyrinth with dead-ends.
- OMT-edge ports stay **open** when the neighbour is the same hẻm type or a road. Use `place_nested` with `neighbors`, e.g. `"neighbors": { "east": [ { "om_terrain": "sg_hem", "om_terrain_match_type": "PREFIX" } ] }` or `"flags": { "east": [ "ROAD" ] }`. They close otherwise via `else_chunks`.
- Because both sides of a boundary use the same fixed port coordinates, alleys match across OMTs **without any shared state**.
- Nested chunks cannot rotate (`src/mapgen.cpp:6383-6384`), so author 4 edge-port "caps" (N/E/S/W) as separate chunks.

**Across OMTs (block-scale labyrinth): yes, with a mutable `overmap_special`.**

- `joins` define alley connectivity between OMTs. Join-conditioned `place_nested` (`"joins": { "north": [ "hem_to_hem" ] }`) opens the matching edge port. Joins used are persisted (`src/savegame.cpp:803`) and fed to mapgen (`src/mapgendata.cpp:118-119`).
- Precedent for narrow meandering linear growth: `data/json/overmap/overmap_mutable/stream.json:12-47`.
- Caveats:
  - mutable placement ignores `must_be_unexplored` (TODO at `src/overmap_special_mutable.cpp:780`);
  - failed growth leaves "unresolved joins" debugmsgs (`:866-890`). Always include closing pieces with `max` in a final phase (doc `doc/JSON/OVERMAP.md:1000-1018`).
- **UNVERIFIED:** using a *mutable* special as a `city_building` pool entry. The loader allows it (`src/overmap_special.cpp:322-336` is not gated by type), and the placement path is generic (`src/overmap_city.cpp:292-294`), but no vanilla city building does it. None of the 414 `city_building` objects in `data/json` are mutable.
  - Validate by adding one to the pool and running the `[overmap]` tests with `--mods=saigon_2000s`.

**Alley-first subdivision at block scale is *not* possible JSON-only.** The city builder decides frontage first (§2.3). Block interiors deeper than 2 OMT remain `field`. They are only *marked* as city by `flood_fill_city_tiles` (`src/overmap_city.cpp:516-559`); they are not built on. JSON workarounds, in order of preference:

1. Deep city buildings with footprint `(0,0)` frontage row plus `(0,1)` hẻm-block. These fill the 3–5-deep blocks when they fit, within 10 retries (`:289`).
2. Infill `overmap_special`s with `"city_distance": [-1, 0]` and `"locations": ["field"]`.
   - `min = -1` is required: the check is `min < dist`, and dist is 0 inside the radius (`src/overmap_special.cpp:214-216`, `src/overmap_city.cpp:500-514`). A max of 0 is legal (`src/common_types.h:39-50`).
   - Density is capped by sector sampling: at most one special per 15×15 sector across both passes (`src/overmap.cpp:3215-3225`, `3338`), i.e. ≤ 144 per overmap.
3. Map-level only: a high-weight `field` mapgen variant that draws squatter or hẻm housing when a `SIDEWALK` neighbour exists (`flags_any`), else plain field.
   - This fixes the look on the ground, but the overmap still shows "field". Mark it cosmetic.

### 4.c Chợ (wet market), large multi-OMT

- **Fixed special, 2×2 or 3×3.** One 2D-`om_terrain` mapgen covers the hall (48×48 or 72×72 rows); a z = 1 roof stack sits above it.
- Stall grid: 4×4 or 6×6 nested slots, each a parameter-selected stall type, following the precedent `data/json/mapgen/cs_market_small.json:45-48`. Stall types are fish tanks, meat hooks, vegetables and dry goods, with `place_loot`/`place_items` per stall.
- Placement choices:
  - As a `shops` pool entry with `"flags": ["CITY_UNIQUE"]` and `"city_sizes": [8, -1]`, so it lands near the centre (`shop_radius`). A 2×2+ footprint only fits the 3–5-wide blocks. Expect frequent failure (10 retries, `src/overmap_city.cpp:289`), and **keep a non-unique fallback in the pool** (B3).
  - As an `overmap_special` with `occurrences`, `city_distance: [1, 4]` and `connections` to `local_road`. The road is then auto-built toward the city centre (`src/overmap_special_fixed.cpp:305-319`), which gives the classic "market at the edge of the grid".
- Street spill-over (chợ tự phát on the adjacent road) cannot be driven by the market's own mapgen, because it does not own the road OMT. Options:
  - put a 2-row frontage strip inside the market OMTs; or
  - add a region `map_extra_collection` for the `road` extras key (map extras are applied per OMT, `src/mapgen.cpp:284-303`). This is not location-aware.

### 4.d Canals (kênh/rạch) through the city

- **The river generator cannot make narrow canals.** Minimum river radius is 2 because of `river_scale = 1 + std::max( 1, river_scale )` (`src/overmap_water.cpp:555`, drawn with `points_in_radius_circ` at `:163`). That is at least 5 OMT ≈ 120 m wide, and its path is a random Bézier (`:69-110`).
- **Streets refuse water** (`src/overmap_city.cpp:318`), and cities are built *after* rivers (`src/overmap.cpp:966` versus `991-997`). Any water present first cuts the grid, with no bridges.
- **overmap_connection reuse (UNVERIFIED, fragile):**
  - A `canal` connection with a LINEAR water oter could be drawn by a special's `connections` entry. `build_connection` supports any linear type (`src/overmap.cpp:2559-2644`).
  - But specials are placed after cities (`:1018`). The path targets the *city centre* (`src/overmap_special_fixed.cpp:312-317`). The greedy path is rejected wherever the connection has no subtype for that terrain (`src/overmap.cpp:2508-2512`).
  - Crossing streets needs a bridge subtype on `road` locations, which would *replace* road line-oters and break intersections.
  - Not recommended for pass 1.
- **Works today:**
  - canals authored *inside* district specials (§7) as dedicated oters: `sg_kenh_ew` (6–8 tile channel, embankment, stilt houses) and `sg_kenh_bridge_ns`;
  - narrow in-OMT water modelled on the vanilla `stream` mapgen (`data/json/mapgen/stream.json`, 2–3 tile channel), placed by a mutable wilderness special (`data/json/overmap/overmap_mutable/stream.json`) for rural rạch outside the city.
- **Pass-1 JSON alternative for real topology:** pre-generated overmaps (§3.2 pattern 3), with canal oters written directly into the z = 0 layer.

### 4.e Saigon River and the delta

- River: `region_settings_river` `river_scale: 3` gives radius 4 ≈ 9 OMT ≈ 216 m. That is realistic for the Sài Gòn river. `river_frequency` and `river_branch_*` control count and braiding (`src/regional_settings.cpp:506-513`, used at `src/overmap_water.cpp:188-214`, `:613`). Placement is random per overmap, continued from neighbours (`:544-690`).
- Delta and mangroves:
  - `forests` swamp thresholds (`noise_threshold_swamp_adjacent_water`, `river_floodplain_buffer_distance_*`, `src/regional_settings.cpp:439-453`);
  - `forest_biome_mapgen` for `forest_water` with nipa and mangrove components;
  - `ocean_start_south`/`east` (`:515-525`) for Cần Giờ-style coast at a fixed overmap distance.
- **No JSON control over *where* the river runs relative to the city.** Only the pre-generated route fixes geography.

### 4.f Dense motorbike parking

- Mechanism: `place_vehicles` with a `vehicle_group` (`src/mapgen.cpp:2715-2757`), with keys `vehicle`, `chance`, `rotation` (int or list), `fuel`, `status`, `faction`. Candidate prototypes: `scooter`, `motorcycle`, `bicycle` (`data/json/vehicles/bikes.json:14,79,213`); `scooter` is a 3-tile `o>o`.
- **Trap:** `map::add_vehicle` defaults to `merge_wrecks = true` (`src/map.h:1855-1858`). Overlapping placements **merge into smashed wrecks** (`src/mapgen.cpp:6964-7060`, with a 200-part cap at `:6971-6975`). Use **fixed, non-overlapping slots**: one bike every 2 tiles along the frontage strip, perpendicular to the curb. Do not use random `x` ranges.
- Where to put them:
  - in the building's own rows 0–1 (the building owns its frontage); and/or
  - by out-weighting `24x24_road_straight_vehicles_city` (chosen only when a `SIDEWALK` neighbour exists, `data/json/mapgen/nested/road_vehicles_nested.json:76-91`) with a Saigon variant. Weights are additive (`src/mapgen.cpp:836`), so give it a very large weight.
- **Performance budget** (§6.3): real vehicles cost every turn. Use at most ~6–10 real vehicles per OMT. Get the visual density of 30–40 bikes from a **furniture prop** ("parked motorbike", smashable into parts), which costs nothing per turn.

## 5. Q5: What needs C++ for authentic topology (pass 2)

Design constraint: at OMT scale the network is **4-connected**. Road oters are LINEAR with 16 line variants (`oter_flags::line_drawing`, `src/omdata.h:293`; `build_connection` uses `om_lines`, `src/overmap.cpp:2586-2640`). "Organic" at overmap scale therefore means:

- irregular spacing, T-junctions, dead-ends, non-rectangular blocks, arterials that zig-zag, and river/canal crossings.

It does not mean diagonals. Diagonal or curved *appearance* belongs to mapgen: a road OMT can draw a diagonal inside itself using neighbour conditions (`road_curved` precedent in `data/json/mapgen/road.json:101-107`).

### 5.2 Determinism and savegame compatibility

- **Determinism contract.** `tests/overmap_test.cpp:1043-1109` asserts identical overmaps from the same RNG engine state.
  - The new code must draw only from `rng_get_engine()`, in a fixed order.
  - Do not iterate `unordered_*` containers while drawing random numbers. `city_tiles` is an `unordered_set`, so sort before use.
  - Noise layers already use `g->get_seed()` and are stateless (`src/overmap_noise.cpp:13-43`). Prefer them for spatial fields such as a density or "old-town" mask.
- **Mapgen C++ (hẻm)** must seed its own local engine from the world seed plus coordinates. It must not consume the global stream, so that visiting order does not change results.
- **Save compatibility:**
  - Already-generated overmaps and submaps are loaded, not regenerated (`src/overmap.cpp:3695-3735`; `MAPBUFFER`).
  - New serialized fields must be optional on load. The loader dispatches by member name (`src/savegame.cpp:555-610`), and older saves simply lack the new member.
  - Renamed Saigon oters need `oter_id_migration` entries (`src/overmap.cpp:1332-1347`, applied `:1382-1397`).
  - Changing `layout` on an existing world only affects overmaps generated afterwards. Document this in the mod as "new world recommended".

## 6. Q6: Performance

### 6.1 Overmap generation (single thread, on demand, can hitch mid-walk)

Cost drivers, all per new overmap:

- **Layer scans.** `place_specials` scans all 21×180×180 = 680,400 OMTs for lake and ocean presence (`src/overmap.cpp:3245-3259`). `generate_sub` always walks every z from −1 down: the comment at `:1057` notes "This forces every sub level to generate". That is 10 × 32,400 cells with two `ter_unsafe` reads each (`:1077-1116`).
- **City building.**
  - Each frontage spot costs up to 10 × (weighted pick + `can_place_special` over the footprint) (`src/overmap_city.cpp:289-303`).
  - Specials with an `eoc` run a dialogue condition per test (`src/overmap.cpp:2981-2986`). **Avoid `eoc` on city buildings.**
  - `lay_out_street` probes a 3×3 neighbourhood per step (`src/overmap_city.cpp:324`).
  - Megacity warns that bigger sizes get "worse and worse" (`src/overmap_city.cpp:157-158`).
  - Saigon wants *more* frontage per OMT. The number of buildings is bounded by street length (∝ size²), so the city builder cost is dominated by the retry loop, not by Saigon content.
- **Road network**: `connect_closest_points` builds O(n²) edges (`src/overmap.cpp:2672-2680`), with one greedy path per accepted edge (`:2726`).
- **Specials**:
  - 144 sectors × ≤ 10 attempts, each reshuffling the whole enabled list (`src/overmap.cpp:3158`, `:3213-3228`);
  - large mutable specials run join resolution per piece (`src/overmap_special_mutable.cpp:843-870`);
  - **mandatory specials that fail cascade into generating a neighbouring overmap** (`src/overmap.cpp:3356-3381`). That doubles the hitch. Keep Saigon mandatory specials few and easy to place.
- **Hidden trigger from runtime mapgen.**
  - `map::generate` samples `overmap_buffer.ter` over ±3 OMT for monster density (`src/mapgen.cpp:249-253`), and `mapgendata` reads neighbours via `overmap_buffer.ter` (`src/mapgendata.cpp:84`).
  - Both go through `get()` (`src/overmapbuffer.cpp:889-893` → `:100-121`), which **generates the neighbouring overmap if it is missing**.
  - So a walk across an overmap border stalls once for the whole generation.
- Measurement (UNVERIFIED numbers until S0.3 builds): `./tests/cata_test --mods=saigon_2000s --durations yes "default_overmap_generation_always_succeeds"` (`tests/overmap_test.cpp:177`). Compare vanilla against the mod. Budget ≤ 1.5× vanilla.

### 6.2 Mapgen per OMT (per column)

- **21 z-levels per call** (`src/mapgen.cpp:226`). Uniform oters skip `draw_map` (`:239`, `:265`). Every **non-uniform** level runs:
  - the full JSON function;
  - map extras (`:284-303`);
  - static spawns;
  - post-process generators (`:346-379`), where riot damage is the default for `generic_city_building`, `data/json/overmap/overmap_terrain/overmap_terrain.json:47`.
- **Consequence:** a z0..z5 nhà ống stack costs about 6× a single-storey building. An OMT whose `sg_nhaong_row_z5` holds only one lot's rooftop water tank still costs a full level.
  - Mitigations: height-banded oters (`_h3/_h4/_h5`); `open_air` above the tallest lot.
- **Nested chunks.** Each `nest()` runs `apply_mapgen_in_phases` (`src/mapgen.cpp:6380-6392`), which **ends with `resolve_regional_terrain_and_furniture` over the whole z-level**: `points_on_zlevel` of the 24×24 smallmap, with 2 flag lookups per tile (`:6289` → `src/mapgen_functions.cpp:2238-2259`).
  - Design in §4.a: 6 lot chunks × (1 lot + 1 sub-chunk) ≈ 12 nests per level ≈ 12 × 576 × 2 ≈ 14k flag tests per level, ≈ 83k per 6-level stack. That is cheap, but it is linear in nest count.
  - **Keep nesting depth ≤ 2 and never nest per tile.** The palette `"nested"` symbol mapping does exactly that; see `earth.json:333-338`, 1×1 chunks per character.
  - There is **no recursion depth guard**; a grep for depth/recursion in `src/mapgen.cpp` found none.
- **Vehicles** make terrain resolve earlier (`src/mapgen.cpp:6419-6425`).
  - `add_vehicle` runs `init_state`, `place_spawn_items` and precalc (`:6890-6897`), then **`rebuild_vehicle_level_caches()` for every vehicle** (`:6917` → `src/map.cpp:596-609`, which iterates all vehicles on all 21 levels).
  - k vehicles per OMT cost O(k²·parts). At k = 10 scooters of about 4 parts each this is negligible; at k = 40 it is noticeable. **UNVERIFIED magnitude.**
- **Items**: shop loot (`place_items`/`place_loot` → `map::place_items`, `src/mapgen.cpp:6709`) is the largest *memory* multiplier. 6 shops per OMT means 6× vanilla's one-shop-per-OMT item count at street level.

### 6.3 Memory and per-turn costs

- **Submap memory.**
  - A non-uniform submap allocates a `maptile_soa` of 144 × {`ter_id`, `furn_id`, `lum`, `cata::colony<item>`, `field`, `trap_id`, `rad`} (`src/submap.h:62-69`, `ensure_nonuniform` `:83-92`).
  - Uniform submaps (`open_air`, rock) allocate nothing.
  - Worked comparison: a 6-level shophouse OMT is 4 × 6 = 24 non-uniform submaps. A vanilla 2-storey house with basement and roof is 4 × 4 = 16.
  - Exact bytes per submap are **UNVERIFIED**. Measure with a `sizeof(maptile_soa)` static_assert/print in a test once built.
- **Per-turn caches.**
  - `build_map_cache` loops every z for outside, transparency and floor caches, gated by dirty flags (`src/map.cpp:10804-10815`). `loadn` dirties all z-levels for each new submap (`src/map.cpp:9328-9335`).
  - The sunlight cache starts at `calc_max_populated_zlev() + 1` (`src/lightmap.cpp:371`). That is the highest non-uniform level in the bubble (`src/map.cpp:11914-11947`).
  - **One 5-storey shophouse anywhere in the 11×11-submap bubble raises the ray-cast start to z = 6 for everything.** In a Saigon street this is always the case, so budget sunlight work at about (6 − player_z) extra levels × 132² tiles whenever the light cache is dirty.
- **Vehicles per turn.** `map::vehmove` visits every vehicle on every level, then runs `vehproceed` up to 100 iterations (`src/map.cpp:922-953`).
  - The bubble is about 5.5 × 5.5 OMT ≈ 30 OMTs. With ~15 street-facing OMTs × 30 bikes that is ~450 vehicles, all ticked every turn. **This is the #1 density risk.**
  - Hence the prop-furniture recommendation in §4.f.

### 6.4 Performance acceptance tests (proposed)

1. `cata_test --mods=saigon_2000s --durations yes "[overmap]"`, compared against the vanilla baseline (`tests/overmap_test.cpp:177`, `:203`, `:1043`).
2. New test `saigon_mapgen_cost`: use `manual_mapgen` (`tests/mapgen_helpers.h:18`) to generate each Saigon oter stack 50 times and assert the mean time is ≤ 2× `house_w_1`.
3. In game: debug-teleport along a 10-OMT street and read the frame time with the `--debug` timings (**UNVERIFIED tooling**). Count `get_vehicles().size()` in the bubble; target ≤ 150.
